# Эффективность Django ORM

Статус: требование пользователя, 13.10.2026. Commerce models и selectors ещё не реализованы.

Запросы находятся в Django adapter/selectors, не в независимом движке. Планировать загрузку данных под конкретную фичу/экран: список каталога, карточка, detail и фильтры имеют разные потребности. Используем штатный ORM, не пишем raw SQL ради предполагаемой скорости.

- select_related для нужных FK/OneToOne; prefetch_related/Prefetch для вариантов, галерей, тегов и других reverse/M2M связей. Prefetch может иметь фильтр, порядок и to_attr для конкретного представления.
- Не запускать запрос на каждый товар, вариант или фото в шаблонах, serializer, property либо цикле. После prefetch не вызывать новые filter/order_by по related manager, если они обходят загруженный результат.
- Каталог ограничен пагинацией; не загружать все товары и все галереи. Для мини-карточки получать только данные выбранного отображения и необходимой матрицы вариантов; detail может загружать больше.
- exists для проверки наличия, count только когда нужен точный счётчик. Не вычислять один и тот же queryset/агрегацию повторно. only/defer применять после проверки, что отложенные поля не создают новые запросы.
- Агрегации/Exists/Subquery использовать для данных фичи при необходимости. M2M фильтры могут дублировать строки: выбрать корректный query shape/Exists или обоснованный distinct, не добавлять distinct вслепую.
- Индексы/constraints исходят из реальных условий фильтрации, сортировки и идентификаторов. Проверять QuerySet.explain и PostgreSQL план на репрезентативных данных; индекс на каждое поле не является целью.
- Bulk операции применять там, где допустим обход save hooks/signals и сохраняются инварианты. Остатки/резервы требуют транзакций и конкурентной корректности, количество запросов не важнее правильности денег.
- Кэш добавлять после исправления query shape и определения invalidation. Персональные данные, цены и наличие не смешивать между пользователями и не выдавать устаревший кэш за подтверждённый остаток.

Приёмка: assertNumQueries или CaptureQueriesContext вокруг конкретного selector/рендеринга; тестировать больше одной карточки и сравнивать разные размеры списка, чтобы выявить линейный N+1. Бюджет запросов устанавливать после реализации фичи, не придумывать единое число для всех экранов. Проверить не только число SQL, но объём выборки и время. Query-count тесты не заменяют PostgreSQL concurrency tests.
