# Отдельный раздел SEO

Дата: 22.10.2026. Статус: reviewed-awaiting-acceptance. Проверка: независимый ревизор (выбран пользователем).

## Исходное поручение и уточнения

«Делай раздел SEO как обсудили: автоматика, поиск страниц, правка текстов и отдельные права доступа. Роли потом, стиль сохраняем, с независимым ревизором».
Предшествующие уточнения: единый раздел вместо обязательной большой SEO-формы товара; администратор также имеет доступ. SEO-специалисту в будущем можно выдать только доступ к SEO, title/description и текстам без изменения цен/остатков/самих товаров. Роли пока не создаются. Используем штатные Django permissions/groups. Интерфейс упрощает работу, технический JSON вторичен.

## Требования

- R1: Управление → SEO в существующем RU/DE кабинете. Обзор, поиск страниц/товаров по названию/SKU/URL, правила автоматики и понятная информация об индексации. Поиск ограничен и пагинирован, не загружает весь каталог. Стиль/компоненты сохраняются; редкие данные раскрываются.
- R2: Автоматические title/meta description по типам страниц; безопасные шаблоны с ограниченными переменными. Ручные исключения для существующих страниц/товаров/категорий/брендов, локаль контента отдельно от языка кабинета. Предпросмотр фактического результата, возврат отдельного поля к автоматическому значению. Текущие данные и ручные SEO категории сохраняются; без тихой перезаписи.
- R3: Редактируемые plain-text описания/вступления в SEO, отображаемые на соответствующей странице покупателю. Отдельный слой текста, без изменения характеристик/цен/остатков/SKU/фото/модели товара. Черновик и публикация разделены, журнал действий без текстового payload, защита от потери параллельных изменений. Предыдущая опубликованная версия и возврат доступны в разумном минимальном объёме.
- R4: Отдельные штатные permissions: просмотр SEO, изменение метаданных, изменение текстов, управление автоматическими правилами, публикация. Серверная проверка GET/POST/действий; права SEO не дают изменение каталога и наоборот. Superuser доступен штатно; роли/группы и права пользователей не назначать.
- R5: Метаданные и JSON-LD используют итоговые актуальные данные автоматически. JSON-LD для просмотра, без произвольного JSON редактора. Реальные рейтинги/цены/остатки не выдумывать. Origin доверенный, staging noindex, private/query политика и демо-защита остаются. Изменения правил не могут включить индексацию или создать произвольные ссылки/HTML.
- R6: Проверки: права отдельно/в комбинациях, сохранение→публичный результат, черновик/публикация/возврат, stale/validation/CSRF/XSS, автоправила, ограничение ORM-запросов, RU/DE desktop/mobile и независимая приёмка. Только добавочные миграции; рабочие товары/заказы/контакты не заполнять и не менять. Доки и затронутый проектный навык актуализировать.

## План

1. Backend исполнитель: модели SEO, публичный resolver/автоправила/метаданные/видимые тексты и tests; согласовать контракт с исполнителем кабинета до зависимой работы.
2. Кабинет исполнитель: формы/views/templates/собственные URL и tests в staff/seo_workspace; отдельные права и UI согласно контракту. Общие nav/locale файлы принадлежат ведущему.
3. Ведущий: nav/URL/locale интеграция, документация, миграции с сохранностью данных, общий прогон, браузер QA. Затем независимый read-only ревизор и исправления.

## Границы

Незакоммиченные изменения предыдущей задачи StoreIdentity сохраняются. Нет разрешения commit/push/deploy, включение индексации, API eBay/Stripe/DHL, внешний AI текстогенератор или передачу текстов/покупателей сервисам. Доступы пользователей и группы не меняем. Рабочую базу изменяем только добавочной схемой; ручные проверки записи — в изолированной QA.

## Ревизия и исправления

Независимый ревизор выявил и после исправления закрыл четыре находки: SEO-поля старой формы категории обходили отдельные права; технический JSON-LD расходился с публичным для HTML-подобного plain text; язык нового RU описания смешивался с языком DE фактических данных; некорректный pasted URL вызывал ValueError. Добавлены соответствующие регрессии. Legacy значения категорий сохранены, форма каталога их не меняет даже при поддельном POST.

Полный прогон до исправлений: 803 passed. После исправлений один старый тест с немецкими текстовыми ожиданиями зависел от оставшейся RU локали; тесту явно задана DE через override, продуктовая логика не менялась. Окончательный полный прогон: **811 passed in 41.82s**. Ruff, Django check, makemigrations --check --dry-run и git diff --check чистые.

Ручная QA: отдельная SQLite8032, сохранён SEO-черновик MANSTORE, публичная страница сохранила прежний title/body; публикация обновила title/meta/body, robots остался noindex; восстановление вернуло автоматические значения. Реальный локальный PostgreSQL использовался только для добавочной миграции. Хеши/количества существующих catalog/order/shop/prefs записей до/после совпали, новые SEO-таблицы пусты (прямая проверка ведущего).

IAB viewport не применился, его неверный промежуточный mobile-снимок заменён настоящим Chrome-снимком. Артефакты: docs/project/visuals/seo-workspace/. Роли/права пользователей не назначались; commit/push/deploy/indexing/внешние API не выполнялись.

Границы: локальная проверка не доказывает production latency/конкурентную нагрузку PostgreSQL или результат Google. Проверки заполнения/длины не являются полным crawler/дубликат-анализом.
