## Требования

- [ ] R1: выдача общего каталога и поиска получает активные товары/варианты из базы; отдельные карточки ведут на соответствующий PDP, без фиксированных demo-моделей и вымышленных счётчиков.
- [ ] R2: поиск и реализованные фильтры отражаются в URL, совместно применяются на сервере; пагинация и пустая выдача сохраняют параметры. Не заявлять работающими элементы фильтрации, для которых нет данных/логики.
- [ ] R3: сохранить HTML-дизайн, sidebar фильтров и компоненты референса, общий header/footer, мобильный принцип показа карточек; не вводить новые модальные фильтры или новый frontend stack. Точный способ подключения desktop/mobile макетов проверить до реализации.
- [ ] R4: выбор цвета/размера использует существующий контракт вариантов: галерея цвета, конкретный SKU/цена, явное отсутствие сочетания. Checkout остаётся явно выключенным; не создавать фальшивое добавление в реальную корзину.
- [ ] R5: ограниченные страницы выдачи, отсутствие N+1 и дублей, проверяемый SQL-бюджет. Django не переносится в engine/worker. GET не создаёт бизнес-данные.
- [ ] R6: не менять реальные данные пользователя, eBay, платежи, DHL, чужие контейнеры и production. Проверять на синтетических данных, сохранять существующие изменения рабочей копии.

## Уточнение реализации — 20.10.2026

Срез включает GET-параметры q, brand/category/tag, color, size, min_price/max_price, in_stock, sort и page. Поиск и фильтры работают в одной выдаче, пары color/size/price/in_stock проверяются у одного активного EUR-варианта. Повторные значения фасетов объединяются внутри одного поля, разные поля совместно ограничивают результат. Размер страницы — 12; SQL-бюджет проверяется на разном количестве карточек. Сортировки — имя и цена; популярность/рейтинги/новизна без надёжных данных не имитируются. Материалы/особые условия остаются визуально в референсе, но отключаются с пояснением. Это решения исполнителя в пределах существующих моделей; они не меняют ограничений R1–R6.

Исторические маршруты каталога/поиска сохраняются для именованных переходов, но используют один серверный контракт. Реальные фотографии и test-количества берутся из уже существующих записей; seed на рабочей базе повторно не выполняется. Корзина остаётся демонстрационной и не получает новые бизнес-операции.
