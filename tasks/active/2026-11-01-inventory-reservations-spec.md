# K4 — локальный склад и резервы: задание на разработку

Дата исследования: 01.11.2026. Статус: шаги1–8 реализованы и независимо проверены в согласованном локальном объёме; reviewed-awaiting-acceptance. Итоги завершающих этапов — в разделах14–15. Пользователь выбрал по одному шагу с полным отчётом и независимым ревизором; результаты — в разделах8–15. Работающая схема/активация отдельно от disposable проверок. Исходные проектные требования ниже сохраняются.

## 1. Поручение и исходное состояние

Пользователь: «Собрать лучшие практики из разных движков/фреймворков и готовых решений по реализации склада и резерва, выдать задачу для разработки, чтобы ничего не упустить».

Сейчас ProductVariant содержит demo_quantity; is_available и ряд фильтров/проверок корзины читают демонстрационное количество. create_test_order в web.orders.persistence атомарно сохраняет TEST order, но не резервирует и не списывает физический запас. Источник истины для настоящего склада ещё не реализован. Не объявлять существующие тестовые заказы реальными продажами.

Сначала строится локальная система. eBay впоследствии подключается адаптером к тем же операциям, а не становится вторым независимым счётчиком. Разрешены только будущие локальные изменения после отдельного поручения; эта подготовка не разрешает внешние операции, commit/push/deploy или изменение рабочих остатков.

## 3. Предлагаемые бизнес-правила первой версии

Это рекомендации для принятия перед зависимой реализацией, а не ранее утверждённые решения:

1. Один склад и одна товарная единица на существующий ProductVariant. Устойчивая внутренняя связь по ID; SKU — уникальный внешний ключ сопоставления, не самостоятельная копия остатка. Смена SKU не теряет историю; при открытых связях произвольное переименование/удаление запрещено или вынесено в отдельную миграцию.
2. Обычное добавление в корзину не резервирует. При финальном подтверждении оформления атомарно создаются заказ, его строки и резерв всех SKU. Нехватка одного SKU откатывает весь заказ/резерв, корзина сохраняется. Дополнительный ранний hold корзины в MVP не нужен.
3. Неоплаченный резерв имеет expires_at. Рекомендуемый начальный срок — 30 минут, конфигурируемый сервером. Это бизнес-настройка, не стандарт отрасли; значение и верхняя граница продления подтверждаются владельцем. Обновление страницы не продлевает срок.
4. Подтверждение принятия/оплаты заказа переводит оставшийся резерв в закреплённый без автоматического таймера оплаты. В K4 это локальная тестовая команда с отдельным правом, без фиктивной реальной оплаты. Для будущих асинхронных способов оплаты нужна отдельная согласованная политика срока.
5. Списание происходит при подтверждённой отгрузке, а не создании этикетки DHL. До будущего shipping-модуля — защищённая локальная TEST-команда/сервис. Снятие с резерва без изменения физического количества — отдельное действие отмены/истечения.
6. Возврат денег не увеличивает склад. Оприходовать возврат можно после получения и проверки качества отдельной операцией. Ожидаемый/повреждённый возврат не доступен к продаже; полноценный RMA и карантинный склад — следующий этап.
7. Backorder, отрицательные продажи и предзаказ в первой версии выключены. Бизнес-нехватка не маскируется обнулением/поправкой чужих резервов.
8. TEST-сценарии изолируются от реального учёта: отдельная тестовая БД/стенд. Будущее live-окружение не принимает TEST-команды к реальному запасу. Миграции не превращают demo_quantity или старые TEST orders в реальный запас/резерв.

Перед началом зависимых шагов разработчик фиксирует принятое правило по сроку, моменту закрепления и границе TEST/live. Если владелец меняет эти правила, обновить это ТЗ, не добавлять скрытые исключения в код.

## 4. Требования с устойчивыми ID

### INV-01. Единый источник количества

- Добавить отдельную inventory-фичу, не переименовывать demo_quantity. Логические сущности: StockBalance, Reservation/ReservationLine, InventoryOperation/Movement. Имена уточняются при проектировании; один класс — один файл.
- Для первой версии `on_hand` означает проверенный пригодный к продаже физический запас. Брак и непроверенные возвраты в него не входят. `reserved` включает временные и закреплённые незакрытые обязательства; `available = on_hand - reserved`. Если разнести temporary/allocated по разным полям, формула вычитает оба ровно один раз.
- Основные ограничения: целые количества; 0 ≤ reserved ≤ on_hand; available ≥ 0; положительный объём команды; уникальный balance на variant/склад; резерв не превышает незакрытое количество строки.
- У каждого счётчика один определённый механизм обновления. Если reserved материализован, он обновляется одновременно со строками резервов, сверяется с их суммой; прямые обходные save/admin/bulk updates запрещены.
- Отсутствующая запись означает «склад не настроен», а не «можно продать по demo_quantity». Инициализация нулём отличается от отсутствия настройки.

### INV-02. Операции и журнал

Команды: начальный остаток, приход, корректировка, временный резерв, закрепление, частичное/полное освобождение, частичная/полная отгрузка, приём проверенного возврата. Минимальный интерфейс сотрудника сначала показывает приход и корректировку; остальные команды доступны через проверяемый сервис и предусмотренный сценарий заказа, без имитации неготовой логистики.

Каждая операция имеет operation_id/idempotency_key, тип, variant/склад, количество/дельты on_hand и reserved, основание, actor либо источник, ссылку на строку заказа/резерв, время UTC и версию остатка. Не хранить клиентский адрес/email в складском журнале. Уникальность бизнес-операции обеспечивается БД.

- Повтор того же ключа с тем же содержимым возвращает прежний результат без второй записи/движения.
- Тот же ключ с другим содержимым даёт конфликт, не «успешный повтор». Ключ связан с типом операции, её владельцем/источником и нормализованным payload; знание чужого ключа не раскрывает чужой результат. Повтор после timeout возвращает прежний результат только после проверки доступа. Секреты и платёжные токены в ключ/ledger не помещаются.
- Журнал append-only на уровне всех прикладных путей и прав; исправления компенсирующими записями. Если нужен запрет для произвольного SQL/DB-администратора — отдельные DB grants/trigger, не заявлять такую защиту без реализации.
- Корректировка на фактически посчитанное количество требует expected revision и сохраняет фактическую дельту. Устаревшая форма не перезаписывает поступившую продажу.
- Уменьшение ниже резерва запрещено обычной командой: показать связанные обязательства и необходимость разбирательства. Зафиксированная недостача не должна молча отменять заказ. Полный workflow инвентаризационных расхождений — отдельное расширение.

### INV-03. Жизненный цикл без двойного вычитания

| Событие | on_hand | reserved | Правило |
|---|---:|---:|---|
| Приход q | +q | 0 | Причина и ключ операции обязательны |
| Новый hold q | 0 | +q | available проверяется под блокировкой |
| Hold → закреплённый резерв | 0 | 0 | Не создать второй резерв на те же q |
| Отмена/истечение q | 0 | −q | Только неотгруженный остаток |
| Отгрузка q | −q | −q | Только из действующего закрепления |
| Принятый пригодный возврат q | +q | 0 | Отдельное основание, без связи с фактом refund |

У строки количество сохраняется: изначально зарезервированное = оставшееся зарезервированное + отгруженное + освобождённое. Истечение — причина освобождения. Переходы закрытых состояний не повторяются. История не исчезает после освобождения.

Одинаковые SKU в запросе агрегируются до проверки, mixed currencies/варианты валидируются существующим checkout. Недопустимы нулевые/отрицательные/нецелые количества, освобождение или отгрузка сверх оставшегося, возврат сверх подтверждённого отгруженного количества за вычетом прежних возвратов. Для независимого возврата без исходного заказа нужен отдельный подтверждённый приход, не поддельная связь с заказом.

### INV-04. Конкуренция PostgreSQL

- Одна короткая transaction.atomic на бизнес-операцию. Все изменяемые stock/reservation/order строки блокируются в документированном общем порядке; SKU блокируются по стабильному ID.
- Проверять доступность после получения блокировки, а не по прежнему JSON/кэшу. Транзакция включает изменения баланса, строк, журнала, привязки к заказу и устойчивого события.
- Создание первой записи защищено unique constraint и обработкой гонки. F-expression само по себе не заменяет проверку всех условий операции.
- Внутри блокировок нет HTTP, писем, ожидания пользователя и долгого импорта. Нужны ограниченные timeout/retry для известных transient DB ошибок, безопасные благодаря idempotency. Не повторять автоматически произвольную бизнес-ошибку.
- DB constraints и сервисные проверки дублируют критические инварианты. Валидация формы одна недостаточна.

### INV-05. Истечение и позднее подтверждение

- expires_at проверяется серверным UTC, граница `now >= expires_at` считается истечением.
- Реализовать bounded `expire_due_reservations(now, batch_size)` и ручной запуск для проверки; автоматический планировщик и повторные вызовы используют тот же идемпотентный сервис. Не создавать задачу/таймер на каждый резерв без необходимости.
- Вставший worker не должен навечно удерживать весь товар: изменяющие операции под блокировкой освобождают просроченные hold для затронутых SKU. GET не выполняет скрытых записей; его консервативный снимок может временно занижать доступность до cleanup, но никогда не разрешает checkout без повторной проверки.
- Cleanup, отмена, закрепление и отгрузка, пришедшие одновременно, дают один допустимый результат. Работник не освобождает закреплённый резерв по старому expires_at.
- Позднее подтверждение истёкшего заказа не воскресает автоматически: повторная атомарная проверка/новый резерв с тем же бизнес-заказом либо состояние «требуется разбор». Никакого автоматического refund/списания денег в K4.
- Ручное продление — отдельное право, лимит и запись причины; не включать бесконечное продление по refresh. Если продление не входит в первый UI, честно оставить действие недоступным.

### INV-06. Связь с существующим магазином

- Заказ, snapshots и резерв создаются согласованно, существующие PRG/CSRF/ownership/idempotency сохраняются. Полные данные запроса не записываются в журнал.
- Существующие старые TEST orders не получают резервы автоматически. Для нового режима явный набор fixtures/seed в QA; миграция рабочих значений без отдельного подтверждения запрещена.
- Единая InventoryAvailability projection используется PDP, каталогом, фильтрами, выбором варианта, корзиной, checkout и кабинетом. In-stock фильтр, сортировки, ценовые/размерные условия должны относиться к тому же подходящему активному варианту.
- В inventory-режиме нет тихого fallback на demo_quantity. Demo-режим, если сохраняется для прототипа, выбирается явно конфигурацией/адаптером; переход описан тестами. Это не разрешение включить реальные продажи.
- Пагинация и ORM select_related/prefetch/Exists/annotations без N+1. Бюджет и размер выборки проверяются для нескольких размеров каталога; не загружать все движения/резервы каждой карточки.
- Не менять суммы, старые snapshots заказов, промокоды, SEO noindex, авторизацию, email или остатки действующего eBay в рамках склада.

### INV-07. Будущая связь eBay

- Несколько listing/вариантов объявления могут ссылаться на один local variant/stock balance. Запас не суммируется по объявлениям. Не строить обратную привязку по названию товара.
- Источники команд: site/staff/ebay и стабильный внешний event/order-line key; семантика заказа отделена от транспорта. Повторный hook/polling-событие не списывает дважды.
- Локальная версия количества и устойчивое `inventory_changed` событие записываются в транзакции. Событие содержит только ID/SKU/версию и минимальное основание; обработчик использует свежую проекцию, а не слепо посылает накопленные старые дельты.
- Подготовить тонкий устойчивый журнал событий/контракт публикации, не отдельную универсальную event-platform. Полный outbox dispatcher/провайдер/письма относятся к K6, если их ещё нет. Отсутствие consumer не теряет изменения; on_commit может будить dispatcher, но не является единственным хранилищем.
- Будущая продажа eBay резервирует/закрепляет тот же запас. Если внешняя продажа уже состоялась, а товара не хватает, событие сохраняется как конфликт для оператора; не теряется и не «исправляется» фальшивым остатком. Реализация импорта/разрешения такого конфликта — отдельный этап eBay.
- Старый снимок eBay не затирает pending local operation. Сверка, watermark/version, пауза, backoff и ручное разбирательство входят в последующий adapter этап.
- У сайта и eBay нет общей DB-транзакции. Абсолютную защиту от одновременной межплощадочной продажи не обещать. На этапе подключения отдельно выбирать channel quota/буфер/распределение последних единиц.
- В K4 тестируется только контракт с fake adapter. Реальных eBay API записей, подписок и изменения объявлений нет; даже чтение API не требуется.

### INV-08. Архитектура и фоновые операции

codex_ecommerce.inventory: публичные DTO/ошибки/правила/операции через минимальные persistence и unit-of-work контракты; без Django/ORM/settings/ARQ/HTTP imports. Django adapter владеет concrete models/migrations, транзакциями, permissions/forms/views, переводами ошибок. Не создавать универсальные repositories, пока не показана их необходимость конкретной операцией.

Redis не является источником количества или единственным местом хранения expiry. Worker ARQ не импортирует Django и не вызывает django.setup(). Для автоматического cleanup выбрать и документировать один имеющийся независимый persistence adapter либо ограниченный внутренний backend API; не дублировать алгоритм обновления счётчиков в worker. До автозапуска обязательны идемпотентность и безопасный ручной запуск. Один владелец миграций.

### INV-09. Простой кабинет и права

«Операции → Остатки», RU/DE, текущие стили и навигация. Список: SKU/товар/цвет/размер, на складе, в резерве, доступно, состояние настройки. Поиск, существующая пагинация, фильтры «не настроено», «нет доступного», «есть резерв», «мало» при заданном пороге.

Карточка SKU: краткий баланс → две основные команды «Приход» / «Корректировка» → вкладки/раскрываемые «Резервы» и «История». Корректировка показывает до/после и влияние; техничные IDs/события вторичны. Не делать стену карточек/JSON или экран ERP.

Раздельные native Django permissions: просмотр баланса/журнала; приход; корректировка; просмотр резервов; действия с резервом/ручное продление; тестовая отгрузка/возврат при их наличии. Просмотр адресов/клиентов не выдаётся складским правом. Меню не заменяет серверные проверки. Роли/группы создавать позже; суперпользователь доступен штатно.

## 5. Критерии приёмки и тесты

Обязательные автоматизированные сценарии, включая реальные отдельные PostgreSQL соединения и transaction tests:

1. Два разных заказа на последнюю единицу: один резерв, второй понятная нехватка; нет отрицательных значений.
2. Заказ нескольких SKU, одного не хватает: ни частичного резерва, ни заказа-призрака.
3. Несколько строк одного SKU агрегированы; повторное оформление не создаёт второй резерв/заказ.
4. Параллельное первое создание balance/операции: unique constraint и корректный результат.
5. Повтор ключа того же payload — no-op/result replay; другой payload — конфликт.
6. Повтор прихода, корректировки, release, commit, shipment и return не повторяет движение.
7. Expiry ровно на границе, после неё, повтор cleanup, два cleanup worker и остановка worker.
8. Expiry против подтверждения/отмены/отгрузки: один допустимый исход, закреплённый резерв не истекает.
9. Частичная отгрузка плюс отмена остатка; все количества сходятся.
10. Запрет отгрузки/освобождения/возврата сверх допустимого остатка; refund без приёмки не меняет склад.
11. Позднее подтверждение: свободный товар успешно переразервирован; уже проданный — разбор без oversell.
12. Корректировка ниже резерва отвергается с объяснением; stale absolute-set не затирает новую операцию.
13. Параллельные многотоварные операции с обратным порядком входа; общий порядок lock и bounded retry.
14. Ошибка на записи ledger/audit/event откатывает и баланс, и резерв, и заказ.
15. Падение после commit до enqueue: durable событие сохранено; повтор обработки не повторяет доменное действие.
16. Удалённый/неактивный SKU, неизвестный склад, нулевые/отрицательные/дробные количества не обходят правила.
17. Отсутствующая inventory запись не берёт demo_quantity; старые TEST orders/working data не изменены миграцией.
18. Согласованная доступность PDP/list/filter/cart/checkout, нужный цвет/размер без подмены варианта.
19. Фиксированное число SQL относительно размера страницы; API не раскрывает чужие резервы/PII.
20. Fake eBay источник дважды прислал одно событие, прислал старый снимок, подтвердил внешнюю продажу при нехватке: локальные контракты не теряют и не удваивают операции; live adapter ещё не реализован.
21. CSRF, staff/nonstaff, каждое permission и поддельные поля actor/user/sku/action; GET ничего не меняет.
22. UTC/DST, длинные RU/DE тексты и безопасное экранирование причины; desktop/mobile и ошибки.

Ручной сценарий в отдельном стенде: приход 2 → заказ A резервирует1 → заказ B резервирует1 → C получает нехватку → отмена A освобождает1 → D может резервировать → TEST отгрузка B списывает физически1 → повтор отгрузки ничего не меняет. Отдельно проверить истечение неоплаченного резерва, сохранение закреплённого, history и восстановление после остановленного cleanup. Без реальной оплаты и DHL/eBay вызовов.

### Решения и ограничения до реализации

Позднее подтверждение выбирает ветку «требуется разбор». Новый резерв с тем же заказом/автоматический возврат денег не реализуются. Отличие EXPIRE от обычного RELEASE сохраняется в журнале; возможная новая ошибка использует стабильный code/action. Время бизнес-решения задаёт trusted backend, не пользователь/worker payload.

Автоматический путь через ARQ готовится opt-in, по умолчанию выключен до явного применения схемы и настройки actor/token/маршрута. Рабочие .env/данные/containers не меняются. Автоматическая activation не выводится из задачи разработать код. Ручной apply тоже проверяется только на disposable fixtures. API только для cleanup, не общий remote-admin. Machine identity ограничена этой операцией и сопоставлена configured persisted staff с expire permission; полные роли/группы не создаются.

Перед основными командами cleanup сохраняет свои изменения отдельными короткими транзакциями, поэтому failed main command не отменяет освобождение. Порядок/CAS и атомарность основной операции сохраняются. Вызов внутри внешней atomic-транзакции нельзя молча объявлять независимым commit: отклонить такой misuse либо дать явно определённый будущий checkout UoW контракт (checkout сейчас не подключается).

### Уточнённый дизайн до реализации

Ref не переиспользуется/продление отсутствует, поэтому ключ устойчив; автор фактического первого действия сохраняется в audit/ledger. Public staff OperationContext этот source не принимает. Backlog в opportunistic path: максимум20 строк одного SKU, затем ExpiryBacklogError с понятным retry action, не скрытый бесконечный drain.

Main auth и original successful replay проверяются до opportunistic maintenance. После очистки expected revision основной команды сохраняется: может потребоваться явное обновление. При due work внутри внешней atomic-транзакции основная команда отклоняется до записи; batch cleanup всегда требует top-level. Существующие no-work команды могут оставаться во внешнем atomic, но это не обещает независимый commit cleanup. Явный release исключает собственный target из precleanup, сохраняя отмену истёкшего HELD; commit закрытого через canonical EXPIRE выдаёт ReservationExpiredError/action review_reservation. Старый успешный replay возвращается раньше этих проверок.

Автоматизация: POST `/internal/inventory/expiry/`, отдельный Bearer token, серверные actor/now/batch. Worker каждые60 секунд вызывает тот же API через bounded stdlib HTTP в executor; только ENV flag1 включает cron. Secrets только environment; Compose template передаёт dedicated настройки web/worker без изменения действующей .env/контейнеров. HTTP допускается только loopback или hostnameweb во внутренней Docker-сети; между хостами HTTPS. Staging SSL redirect/Basic Auth/ALLOWED_HOSTS не обходятся заголовками, их отдельная deployment-настройка не входит в текущие изменения.
