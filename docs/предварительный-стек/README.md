# Предварительный стек

Дата проверки источников: 11.10.2026. Это список кандидатов для прототипа, а не установленный стек и не обязательство покупать подписки. Магазин: Германия, немецкий язык, мужское бельё MANSTORE, Olaf Benz, CALIDA; действующий канал eBay сохраняется.

Подробно: [Koongo — возможности, синхронизация, тарифы и подключение Django](koongo.md).

Уточнения от 13.10.2026: [прямая синхронизация eBay, карточка с вариантами и импорт фотографий](catalog-ebay-photos.md). Это текущая основа прототипа; Koongo остаётся альтернативой.

План подготовки и реализации: [документация проекта](../README.md). Первая демонстрация — каталог, варианты и фотографии; checkout следует отдельными этапами.

## Основа

| Задача | Предварительный выбор | Что делаем сами |
|---|---|---|
| Приложение | Django + PostgreSQL; codex-django, scaffold необязателен | Каталог, варианты, корзина, заказы, кабинет |
| Интерфейс | Django Templates, HTMX, Alpine | Быстрые страницы, выбор размера/цвета и наличие конкретного варианта |
| Фоновые задачи | ARQ + Redis; независимый worker пакет/контейнер | Синхронизация, изображения, письма, повторяемые задачи |
| Внешние REST API | httpx; отдельные адаптеры | Таймауты, нормализация ошибок, ограничения запросов |
| Оплата | Stripe Checkout hosted + PayPal через Stripe; официальный Python SDK `stripe`, один платёжный API | Сначала sandbox; карты/PayPal, проверенные webhooks, статусы и полные/частичные возвраты по подтверждению сотрудника |
| Доставка | Напрямую DHL: Shipping + Pickup + Tracking API; свой адаптер на `httpx` | Этикетки из заказа; групповой забор одной кнопкой; статус и история посылок в кабинете покупателя. Доступ и квоты — по договору; возвраты уточняются отдельно |
| eBay | Прямой адаптер eBay API; Koongo как альтернатива | Связь существующих объявлений с вариантами, синхронизация доступного количества, сверка и журнал ошибок |
| Фотографии | Hetzner Object Storage + django-storages/boto3 + Pillow | Размеры и форматы, кеширование |
| Возвраты | Напрямую DHL Returns API + Tracking API | Выбор товаров в кабинете, PDF и QR, отслеживание возврата; проверка посылки сотрудником и отдельное возмещение через PSP с учётом обязательных сроков |
| Юридические тексты | IT-Recht Kanzlei; Händlerbund как альтернатива | Приём/обновление текстов, локальные страницы |
| Cookie consent | django-cookie-consent при необходимости | Подключение аналитики только после нужного согласия |
| Письма | Существующий почтовый backend codex/Django + transactional SMTP | Письмо с трек-номером после фактической передачи курьеру, не создания этикетки или заявки на забор; защита от дублей и безопасный повтор при сбое. Провайдер после проверки договора |
| Документы заказа | HTML → PDF через WeasyPrint при необходимости | Представление счёта; бухгалтерия остаётся отдельной интеграцией |

Версии пакетов фиксируем после проверки совместимости в прототипе. Не устанавливаем всё сразу. Первый работающий сценарий: каталог → вариант → корзина → заказ → тестовая оплата → письмо. Прямой eBay-адаптер и доставка подключаются следующими этапами; полноценный импорт заказов eBay в начальный объём не входит.

## Собственные модули

Предполагаемая структура будущего кода:

```text
src/
  shop/                 # Брендинг, немецкие тексты, правила конкретного магазина
  codex_ecommerce/       # Переиспользуемая логика торговли
    catalog/            # Товар и варианты SKU: размер, цвет, EAN
    inventory/          # Остатки, резервы, освобождение резервов
    orders/             # Заказы, строки и снимок цен на момент покупки
    payments/           # Контракты и адаптеры оплаты
    shipping/           # Контракты и адаптеры доставки
    channels/           # Koongo/eBay и сопоставление идентификаторов
    legal/              # Версии текстов и интеграции провайдеров
```

Это схема, папки кода пока не созданы. Сначала проверяем модули внутри магазина; в самостоятельную библиотеку выносим устойчивые контракты. Возможности кабинета, SEO, настроек и уведомлений используем из существующих codex-библиотек после проверки, не копируем их заново.

Курсовой `CodexDLC/e-comercial` можно использовать как источник наработок каталога, корзины и заказов. Для реальной торговли отдельно нужны варианты, конкурентное резервирование остатков, идемпотентность webhooks, возвраты и синхронизация каналов. Наличие кода не подтверждает готовность этих сценариев.

## Важные контракты

- Остаток принадлежит SKU, а не только товару. Источник истины и правила синхронизации с eBay выбираем до подключения продаж.
- Webhook может прийти повторно и в другом порядке. Одно событие не должно дважды списать остаток или отправить заказ.
- Успешное открытие страницы после оплаты не является подтверждением платежа.
- Внешняя синхронизация выполняется в фоне с журналом ошибок. Повторять можно только операции, для которых предусмотрена защита от дублирования.
- Юридические тексты и фотографии доступны локально/из хранилища; сайт не запрашивает провайдера при каждом просмотре.

## Что выяснить перед прототипом

1. Где сейчас ведутся SKU, EAN и остатки; есть ли выгрузка товаров и связь с существующими eBay listings.
2. Доступ eBay API, типы существующих listings, идентификаторы вариантов и фактические квоты приложения; структура папок/имён фотографий после сортировки шефа.
3. Существующий договор доставки, бухгалтерская программа и способы оплаты, нужные покупателям.
4. Выбранный юридический пакет для собственного Django-магазина и доступ к его спецификации.

Прототип начинаем с тестовых товаров и sandbox-платежей. Оценка ресурсов появится после проверки этих интеграций. Два сервера и высокая доступность — отдельный этап; S3 само по себе не решает отказоустойчивость базы.

Уточнения архитектуры 13.10.2026: [правила кода](../../AGENTS.md), [выбор оплаты](../project/payment-selection.md). Scaffold проверяем на ненужный booking; движок независим от Django с первого этапа, основной worker — только ARQ.
