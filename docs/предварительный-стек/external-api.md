# Внешние API и Python

Проверено по официальным источникам 11.10.2026. Конкретные тарифы, доступ аккаунта и договоры пока не проверены. Для старта выбираем одного провайдера на задачу.

## Оплата

Решение владельца от 15.10.2026: **Stripe Checkout hosted + PayPal через Stripe**, один платёжный API, сначала только sandbox. Официальный Python SDK `stripe` используется в независимом адаптере вне движка; второго прямого PayPal adapter в первой версии нет. Карты, PayPal, статусы и полные/частичные refunds обслуживаются через Stripe; возвраты подтверждает сотрудник, webhooks проверяются и дедуплицируются.

Немецкий аккаунт бизнеса, EUR. Надбавка Stripe за PayPal: 0,2% + 0,10 € сверх PayPal-тарифа. При PayPal Checkout DE 2,99% + 0,35 € получаем 3,19% + 0,45 €, около 2,20 € на заказе 55 €. Индивидуальные условия подтверждаем до live. [Stripe DE](https://stripe.com/de/pricing/local-payment-methods).

[Выбор и пользовательский поток](../project/payment-selection.md), [сравнение комиссий](../project/payment-provider-comparison.md). Ранее рассмотренный Mollie остаётся альтернативой, не выбранной интеграцией. Реальные платежи не активированы.

## Доставка

**Решение от 15.10.2026: напрямую DHL**, без обязательного посредника Sendcloud. Python: собственный адаптер поверх официальных HTTP API через `httpx`. Это зафиксированный план интеграции, не реализованная функция.

- **Создание отправления и печать этикетки из заказа:** получатель и адрес автоматически берутся из заказа; отправитель — из настроек магазина. Сотрудник подтверждает вес и услугу доставки. Через DHL Parcel DE Shipping API создаём отправление, сохраняем номер отслеживания и PDF-этикетку у заказа. Этикетка доступна для скачивания и печати из кабинета. Печать означает подготовку документа; автоматическая отправка на локальный принтер требует отдельного решения.
- **Забор нескольких готовых посылок одной кнопкой:** сотрудник выбирает подготовленные отправления, дату и согласованную точку забора. Через DHL Parcel DE Pickup API отправляем одну заявку на эту группу посылок; сохраняем идентификатор, состав и статус заявки. Поддерживаем проверку статуса и отмену, если это допускает DHL. Создание этикетки само по себе не заказывает курьера.
- **Надёжность:** повторное нажатие не должно создавать дубли отправлений или платных заявок. При неопределённом результате запроса сначала сверяем состояние с DHL; не выполняем слепой повтор. Повторная печать использует уже сохранённую этикетку.
- **Отслеживание в кабинете покупателя:** получаем статусы напрямую от DHL через Tracking API; возможность Push-уведомлений проверяем для нашего договора и типа отправлений. ARQ обновляет локально сохранённые статус и историю движения; открытие кабинета не вызывает обязательный синхронный запрос к DHL. Показываем трек-номер, ссылку DHL, статус, историю и время последнего обновления. Покупатель видит только отправления своих заказов. При нескольких посылках у заказа отслеживаем каждую отдельно.
- **Письмо после передачи курьеру:** создание этикетки означает «Подготовлено к отправке» и не запускает письмо «Заказ отправлен». Основание для письма — подтверждённая сотрудником фактическая передача посылки курьеру либо подходящее событие DHL о приёме посылки. Создание заявки на забор также не подтверждает передачу. Письмо отправляет наш почтовый сервис через фоновую задачу; в нём номер заказа, трек-номер и ссылка отслеживания. Повторные события или нажатия не создают повторных уведомлений; неудачная отправка письма допускает безопасный повтор. При частичной отправке указываем переданные посылки и не объявляем весь заказ отправленным.
- **Разделение кода:** Django хранит связь с заказом и предоставляет действия сотрудникам; отдельный ARQ worker выполняет фоновые HTTP-операции через независимый адаптер. Движок не импортирует Django, ARQ или `httpx`.

Перед подключением подтвердить бизнес-договор, доступ к Shipping/Pickup/Tracking API, расчётные реквизиты DHL, адрес, допустимые даты/сроки заявки и стоимость забора. Для tracking уточнить квоты, доступность Push и сопоставление событий приёма посылки. Для возвратов подтвердить доступ Returns API, receiverId и расчётный номер; сценарий описан ниже. Все перечисленные функции пока являются планом реализации.

Официальные источники, проверенные при обсуждении 15.10.2026: [DHL Parcel DE Shipping](https://developer.dhl.com/api-reference/parcel-de-shipping-post-parcel-germany-v2), [DHL Parcel DE Pickup](https://developer.dhl.com/api-reference/parcel-de-pickup-post-parcel-germany).

Отслеживание: [каталог API Post & DHL Germany](https://developer.dhl.com/post-and-dhl-germany?language_content_entity=en), [Shipment Tracking Unified — Push](https://developer.dhl.com/api-reference/shipment-tracking-unified-push).

## Возвраты: напрямую DHL

Решение от 15.10.2026, пока без реализации:

- Покупатель выбирает в своём заказе товары и количество для возврата. Магазин проверяет принадлежность заказа, уже возвращённые количества и создаёт отдельную заявку; несколько позиций можно объединить в одну возвратную посылку.
- Через DHL Parcel DE Returns API получаем PDF-этикетку и QR-код для возврата из Германии. В кабинете доступны скачивание PDF, показ QR и текстовый RET-номер рядом с QR; инструкцию можно продублировать письмом. Адрес магазина берётся из настроенного DHL `receiverId`, адрес отправителя — из подтверждённых данных покупателя. Нужны активная услуга Retoure и receiverId с расчётным номером; стоимость возврата определяется отдельно.
- Сохраняем связь заявки, выбранных позиций, посылки и трек-номера. Напрямую через DHL обновляем статус обратной доставки и показываем его покупателю. Повторное скачивание не создаёт новую этикетку; повторные события не дублируют операции.
- Рабочий процесс: заявка → этикетка выдана → передано DHL → получено магазином → проверено сотрудником. Сотрудник фиксирует фактически полученные позиции, количество и состояние. Приёмка не возвращает товар автоматически в доступный для продажи остаток.
- Возврат денег — отдельная операция через исходного платёжного провайдера после проверки посылки в обычном рабочем процессе. Ни выдача этикетки, ни статус DHL «доставлено» сами по себе не запускают выплату. Поддерживаем частичное возмещение, устойчивый ключ операции и сверку результата при сбое; сумма не превышает оставшуюся доступную к возврату сумму.
- Этот рабочий порядок не должен блокировать обязательный по закону возврат средств до окончания внутренней проверки: для Widerruf учитываем сроки и предоставленное покупателем подтверждение обратной отправки. Нужны отдельные дата уведомления об отказе, доказательство отправки, срок возврата денег и предупреждение сотруднику о сроке. По § 357 BGB удержание выплаты связано с получением товара **или** доказательством отправки; проверка склада не является безусловным основанием дополнительной задержки. Окончательные правила согласуются с юридическим пакетом магазина.

Источники: [DHL Parcel DE Returns](https://developer.dhl.com/api-reference/dhl-parcel-de-returns-post-parcel-germany), [§ 357 BGB](https://www.gesetze-im-internet.de/bgb/__357.html).

## Прямой eBay API — основной вариант для прототипа

Уточнение требований от 13.10.2026: синхронизируем доступное количество по вариантам существующих объявлений. Полный импорт заказов, адресов покупателей и организация отправки eBay-заказов из сайта сейчас не требуются. Подробности: [каталог, остатки и фотографии](catalog-ebay-photos.md).

Python: собственный адаптер поверх HTTP API, фоновые задачи и OAuth-доступ продавца. API обновления выбираем по модели существующего объявления, не мигрируем listings автоматически. [Inventory API](https://developer.ebay.com/develop/api/sell/inventory_api), [Trading ReviseInventoryStatus](https://developer.ebay.com/Devzone/XML/docs/Reference/eBay/ReviseInventoryStatus.html).

Интервал проверки выбираем после проверки методов, квот и доступности уведомлений для аккаунта. Частота 10 секунд обсуждалась как возможность, а не утверждённое требование. [Квоты API](https://developer.ebay.com/develop/api/sell/api_call_limits).

## Koongo — альтернативный вариант

Custom platform может передавать товары через доступный по URL feed. Koongo поддерживает eBay на уровне заказов, но для собственного магазина детали order API нужно согласовать с поддержкой. Наличие коннектора не подтверждает готовую двустороннюю интеграцию Django. [Custom platform](https://www.koongo.com/platform/custom-platform/), [настройка feed](https://help.koongo.com/en/articles/8582736-koongo-settings-for-custom-platforms), [поддержка заказов](https://help.koongo.com/en/articles/8582844-which-marketplaces-and-platforms-does-koongo-support-at-order-level).

Python: генератор feed + `httpx` для документированного API. Проверить привязку к существующим listings по SKU/EAN/item ID, импорт заказов, отмены, возвраты и задержку обновления остатков. Периодический feed не равен мгновенному резервированию: нужен согласованный механизм защиты от перепродажи последней вещи.

Koongo MCP может помогать исследовать и настраивать интеграции. Для постоянной работы магазина используем поддержанный runtime API/feed и фоновые задачи; наличие MCP не заменяет этот контракт. [MCP concepts](https://help.koongo.com/en/articles/16527805-overview-concepts).

## Хранилище и изображения

**Hetzner Object Storage** предоставляет S3-совместимый API. Python: `django-storages[s3]`, `boto3`, собственный endpoint и credentials. Исходники и производные изображения храним раздельно. [Hetzner](https://docs.hetzner.com/storage/object-storage/faq/buckets-objects/), [Django backend и endpoint_url](https://django-storages.readthedocs.io/en/latest/backends/amazon-S3.html).

**Pillow** — размеры и генерация WebP/AVIF в фоне. Доступность кодеков проверяем в Docker-образе: поддержка формата зависит от сборки. Не преобразовываем все исходники при каждом запросе. [Форматы Pillow](https://pillow.readthedocs.io/en/stable/handbook/image-file-formats.html).

## Письма и документы

Для старта достаточно Django SMTP/backend существующей библиотеки и transactional-провайдера. Если нужен API, **Postmark** имеет документацию и официальные библиотеки, включая Python. До выбора проверяем договор обработки данных, условия передачи данных, доставляемость и цену; провайдер пока не выбран. [API](https://postmarkapp.com/developer/), [официальные библиотеки](https://www.postmarkapp.com/developer/integration/official-libraries).

**WeasyPrint** генерирует PDF из HTML/CSS, удобно для документов заказа. Требует системных зависимостей, поэтому проверяем в Linux-контейнере. PDF не заменяет бухгалтерскую систему и структурированную электронную фактуру. Сначала выясняем, какой сервис учёта уже использует магазин. [Документация](https://doc.courtbouillon.org/weasyprint/stable/first_steps.html).

## Поиск и аналитика

Существующие Google suggestions/Semrush выгрузки остаются исследовательским инструментом в `analysis/`, не частью checkout. Подсказки дают варианты фраз, но не частотность; сохранённые показатели Semrush — оценки за месяц и снимок на дату сбора. SEO-страницы строим из реальных товаров/категорий. Merchant feed, Search Console и аналитика — последующие интеграции после появления домена и сайта.

## Общий слой интеграций

Credentials через окружение/секреты, не в репозитории. Для каждого адаптера: sandbox, таймауты, обработка ошибок, минимальные журналы без чувствительных данных, тестовые ответы API. Подписи и авторизацию webhook реализуем по спецификации конкретного провайдера. Повторные попытки и идемпотентность проектируем вместе, особенно для платежей и отправлений.
