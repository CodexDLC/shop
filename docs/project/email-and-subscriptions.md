# Письма и рекламные подписки

Статус 16.10.2026: подтверждение email и сброс пароля оформлены HTML + plain text в стиле согласованных макетов; локальная доставка через Mailpit. Подписки, кампании и письма заказов пока требования. Внешняя отправка не подключена.

## Типы писем

Транзакционные: получение заказа, подтверждение платежа при необходимости, отправка/tracking, отмена, частичный/полный возврат, существенное изменение заказа, восстановление пароля и проверка email. Заказ, оплата и отправка — разные статусы; шаблон не утверждает оплату/отправку без подтверждения события.

Маркетинговые, последующий этап: newsletter, новые коллекции, акции и подборки. Напоминание о брошенной корзине, просьба об отзыве и back-in-stock не становятся автоматически транзакционными только по названию; основание и разрешение проверяются отдельно. Не добавлять рекламные блоки в обязательные уведомления без проверки.

## Подписка

Консервативное правило проекта — явная добровольная opt-in подписка с double opt-in (DOI). DOI — выбранный способ подтверждения адреса/доказательства, не утверждение, что закон предписывает единственную реализацию.

- Отдельная необязательная, изначально пустая галочка рекламы, не объединённая с условиями покупки/cookies. Покупка возможна без подписки.
- Покупка, регистрация, eBay order или импорт адреса сами по себе не активируют рекламу. Cookie consent и email marketing consent — разные записи.
- Состояния: неподписан → pending confirmation → subscribed → unsubscribed. Неподтверждённому адресу не отправляем кампании; DOI письмо без рекламы, срок токена и ограничение повторов.
- Подтверждение не происходит при простом GET из-за scanners/prefetch почтовых клиентов: ссылка открывает страницу, явное действие подтверждает подписку.
- Доказательство: нормализованный email, цель/канал, версия показанного текста, источник формы, времена запроса/подтверждения/отзыва. IP/user-agent только при обоснованной необходимости и правилах хранения; не копировать лишние PII в логи.
- Отписка без входа/оплаты, заметная в каждом рекламном письме, с минимальными действиями. Страница управления предпочтениями не должна мешать полному отказу.
- Поддержать provider one-click unsubscribe при выборе транспорта; GET не должен случайно подписывать или выполнять другие опасные операции. Токены непрозрачные/подписанные, не email в URL; повтор отписки безопасен.
- Новый opt-in после отказа требует нового подтверждения, старый токен не восстанавливает подписку.

Правовой контекст: §7 UWG регулирует email-рекламу и содержит ограниченное исключение для существующих клиентов; в прототипе это исключение не используем без отдельной проверки. Отзыв согласия должен быть простым. [§7 UWG](https://www.gesetze-im-internet.de/uwg_2004/__7.html), [разъяснение Еврокомиссии](https://commission.europa.eu/law/law-topic/data-protection/information-business-and-organisations/legal-grounds-processing-data_en).

## Отправка и отказ

Шаблон/событие имеет явную категорию transactional или marketing. ARQ — отдельный отправитель без Django, использует нормализованный payload и independent rendering/transport adapters. Django сохраняет изменения подписки и передаёт контракт; API не требует передачи web-пакетов worker. Перед реализацией проверить codex-django messaging / codex-platform messaging skills, не писать второй campaign engine без проверки существующего.

Маркетинговый worker повторно проверяет актуальную подписку/suppression непосредственно перед отправкой, а не только при создании списка кампании. Отписка отменяет ожидающие отправки; уже переданное транспорту письмо невозможно гарантированно отозвать. Bounce/complaint подавляют дальнейшую отправку по правилам; provider callbacks аутентифицированы и идемпотентны.

Отказ от рекламы не отключает необходимые письма о текущем заказе. Разные типы suppressions не смешиваем. Не удаляем отказ так, чтобы следующий импорт снова включил человека в рассылку; минимальное хранение suppression и доказательств согласуется с правилами retention.

Повторы очереди не должны отправлять одно событие бесконечно; сохраняем delivery IDs/status и учитываем неопределённый исход транспорта после timeout. Не обещаем exactly-once delivery, если транспорт не предоставляет соответствующую гарантию.

## Дизайн писем

Отдельный email layout: логотип, цвета магазина, безопасные font fallbacks, ясная кнопка, адрес поддержки и необходимые сведения отправителя. Внешние web-fonts не являются обязательными для чтения письма. HTML с inline-compatible CSS + text/plain, absolute URLs, корректность без загрузки картинок; не использовать site CSS/JS.

Общий стиль и шаблоны:

1. Подтверждение заказа с составом/суммой и проверенным статусом.
2. Отправка/tracking.
3. Отмена и возврат денег.
4. Сброс пароля/проверка адреса.
5. DOI подтверждение и страница истёкшего/использованного токена.
6. Рекламная подборка и подтверждение отписки/предпочтения.

Tracking pixels и персональное отслеживание ссылок по умолчанию выключены, требуют отдельной проверки основания/согласий. Настройку SPF/DKIM/DMARC и signed provider webhooks проверяем при выборе почтового сервиса.

## Приёмка

Покупка без галочки; pending не получает рекламу; GET/scanner не подписывает; повтор DOI не дублирует запись; отписка отменяет queued campaign; старый token не подписывает после отказа; импорт не сбрасывает suppression; необходимые order emails остаются доступными. HTML/plain text читаются без картинок; реальные суммы/адреса защищены и не попадают в логи.


## Реализованное оформление auth-писем

Шаблоны customer/templates/account/email, общий base_message.html: тёмно-зелёная шапка, вложенный PNG-логотип, светлый фон, таблицы presentation и inline CSS. Системные Arial/Georgia вместо внешних web fonts; никаких скриптов, трекеров и внешних картинок. ShopAccountAdapter добавляет логотип CID только к подтверждению email и password reset; остальные письма allauth не менялись. Тексты — ключи email.* в de.json; обычный текст сохраняет исходную ссылку без HTML escaping. Токены и подтверждение по-прежнему принадлежат allauth. Не переносить макетные обещания сроков и маркетинг в обязательные уведомления.

Проверка: три prefix-варианта, multipart HTML/text, CID, escaping ссылок и отсутствие внешних ресурсов; 34 auth/email tests passed. Chromium preview desktop/mobile без горизонтального overflow, PNG отображается. Это проверка браузером и Mailpit, не сертификация Outlook/Gmail. Evidence: visuals/emails. Реальная регистрация использует эти шаблоны после перезапуска; в Mailpit отправлен отдельный пример с темой [Vorschau], без рабочего токена.
