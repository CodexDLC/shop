# Архитектура

Статус 15.10.2026: web-фичи catalog/cart/orders/payments/customer/support, их namespaces/templates и persistence-основа созданы; данные интерфейса пока presentation-моки. Доменный commerce API и реальное исполнение остаются следующим этапом. [Текущий перенос](django-template-migration.md), [ключи локализации](django-localization.md).

План: независимый Python-движок + Django web с PostgreSQL, Django Templates, HTMX и Alpine. ARQ + Redis — отдельный потребитель API движка. Правила: [AGENTS.md](../../AGENTS.md).

```text
src/
  web/                    # Django config, shop, ORM/adapters, templates
  workers/                # Самостоятельный ARQ пакет и зависимости
  codex_ecommerce/         # Кандидат на будущую библиотеку
    catalog/
    inventory/
    orders/
    payments/
    channels/
    media_import/
    shipping/
tests/
deploy/                   # Конфигурация контейнеров после выбора runtime
```

Базовые пакеты web, workers и codex_ecommerce созданы; перечисленные commerce-фичи остаются планом. Web и ARQ собираются в отдельных контейнерах, Django не переносится в worker. Celery допускается только для обоснованных сверхтяжёлых задач отдельно. Границы модулей не требуют микросервисов.

## Ответственность

| Модуль | Ответственность |
|---|---|
| catalog | Товар, варианты SKU, размер/цвет, цена, связь галерей |
| inventory | Физический остаток, резерв и доступное количество |
| orders | Только заказы сайта, снимок состава/цен, переходы статусов |
| payments | Контракт оплаты, provider adapter, события и возвраты |
| channels | eBay binding, чтение/запись количества, сверка и журнал синхронизации |
| media_import | Инвентаризация, сопоставление, проверка, загрузка и производные фото |
| shipping | Отправления и provider adapters на последующем этапе |

HTTP-клиенты не содержат правила корзины и остатков. Бизнес-операции вызывают адаптеры через явные контракты; библиотека не зависит от названия магазина или конкретной схемы папок шефа. Схему моделей и миграции утверждаем на этапе реализации.

Существующие codex-библиотеки сначала проверяем на реальные подходящие возможности, затем используем. Не копируем уже готовые кабинеты/SEO/настройки. Из курсовой берём проверенные наработки, а не считаем весь проект готовой commerce-библиотекой. Извлечение codex_ecommerce — после работающего прототипа и стабильных границ.

## Остатки и внешние события

Локальные изменения выполняются транзакционно. Предстоящие внешние обновления сохраняются устойчиво, отправляются worker и подтверждаются отдельно. Повтор операции не должен повторно списывать количество. Старый снимок eBay не перезаписывает локальное изменение, которое ещё не подтверждено.

Webhook — сигнал/событие, не универсальное доказательство текущего состояния. Конкретная схема reconciliation зависит от выбранных API, ручных правок и источника истины; это открытое решение, не готовый алгоритм. Минимальные события продаж не превращаются автоматически в полноценные заказы сайта.

## Изображения

Исходник → сопоставление модели/цвета → подтверждённая галерея → производные размеры. Общая галерея цвета используется всеми размерами. Повторный импорт сохраняет ручные решения. На уровне задания храним статус и причину ошибки; импорт больших архивов не выполняем внутри HTTP-запроса.

Повторный импорт сохраняет также выбранное главное изображение и ручной порядок галереи.

## Включение eBay

По умолчанию read-only/dry-run: показываем предполагаемые изменения без записи. Пилот ограничиваем списком SKU, предусмотрены пауза синхронизации и время последней успешной сверки. При quantity=0 не завершаем listing автоматически: проверяем сохранение item ID и поддерживаемое поведение out-of-stock для фактического типа объявления.

## Независимость движка

Движок изначально не зависит от Django, ORM и очереди. Команды/DTO → результаты/доменные ошибки; API вызывается и Django, и ARQ. Persistence/транзакции задаются через контракты. Django ORM adapter остаётся в web; worker использует независимый adapter либо явный backend API. Общей схемой хранения управляет один набор миграций. Извлечение в отдельный distribution может быть позже, независимость соблюдается сразу.

Один класс — один файл; многоклассовый модуль превращается в пакет. __init__ служит экспортам. Штатные возможности Django максимально используются в web.
