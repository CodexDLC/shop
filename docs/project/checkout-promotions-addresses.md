# Локальное оформление: промокоды и адреса

Статус 20.10.2026: реализовано для локальных TEST orders. Сохраняется текущий HTML/reference дизайн. Это не Stripe sandbox и не интеграция DHL.

## Промокоды

- `cart.PromoCode`: один код на корзину, ASCII uppercase до32 символов; фиксированная EUR-скидка или процент до100%, активность, начало/конец действия, минимальная стоимость товаров. Новые правила выключены по умолчанию. Создание/редактирование через Django admin `/admin/cart/promocode/`; в действующую локальную БД образцовые коды не добавлены.
- Денежная логика `codex_ecommerce.cart.DiscountRule/discount_amount` независима от Django: только Decimal, EUR, точность центов, ROUND_HALF_UP, скидка не больше стоимости товаров. Сумма доставки сейчас0 и явно тестовая; скидка применяется к товарам.
- В корзине сохранён accordion: native POST+CSRF apply/remove, код хранится отдельно для guest/user principal. Произвольный браузерный amount не принимается. При удалении/истечении/изменении условий выбранного кода текущая корзина пересчитывается; недействительный код блокирует checkout, его можно удалить/заменить.
- Правила перечитываются на review/create; fingerprint включает текущие цены, адреса, суммы и подпись условий кода. В atomic-транзакции блокируются SKU и используемое правило. Снимки subtotal/discount/coupon/total не меняются после сохранения заказа. Уникальный intent не допускает второго заказа при повторном submit.
- Stacking, лимит применений, персональные коды, правила по товарам, production VAT/refund allocation не реализованы. Это следующие возможности, не скрытые ограничения действующей акции.

## Адреса

`CheckoutAddressForm` принимает старый домашний POST и новые ветки `home/packstation`, `billing_separate`. По умолчанию обычный адрес доставки становится платёжным. При отдельном платёжном адресе нужны имя, фамилия, улица/дом, пятизначный PLZ, город и DE. Неактивные поля очищаются до валидации.

Packstation: имя получателя, личная Postnummer6–10 ASCII цифр, трёхзначный номер станции, PLZ/город станции, DE. Каноническая строка доставки — `Packstation NNN`; нужен отдельный обычный платёжный адрес. Название Packstation не принимается как домашняя улица. Формат сверён с [DHL: получение](https://www.dhl.de/de/privatkunden/hilfe-kundenservice/packstation/empfangen.html) и [Parcel DE Shipping API](https://developer.dhl.com/api-reference/parcel-de-shipping-post-parcel-germany-v2?language_content_entity=de). Существование станции, соответствие Postnummer человеку и пригодность конкретной посылки не проверяются; никаких запросов/этикеток/заказов DHL нет.

Оба адреса видны в review, confirmation и существующем просмотре тестового заказа в кабинете. Хранятся отдельными JSON snapshots `Order.address/billing_address`, не ссылками на изменяемый профиль. Для прежних заказов новые поля не заполняются выдуманными данными: subtotal nullable, billing пустой.

Без JS все ветки доступны как обычные поля, сервер решает, какие обязательны. JS только раскрывает/скрывает ветки, включает billing для Packstation и отключает неактивные поля. Условная логика и расчёт сумм не зависят от JS.

## Данные и проверка

Адреса/Postnummer не передаются наружу и не логируются новым кодом; используются существующая session и принадлежащий покупателю TEST order. Новых tracking SDK/рассылок/cookies кроме существующего функционального контура нет. Сроки удаления тестовых данных/backup recovery задаются отдельной эксплуатационной политикой до публичного запуска.

Добавочные миграции: cart0002 и orders0004. Локально применены, предыдущие строки заказа сохранены. Изолированные тесты включают положительные промокоды, округление, подмену сумм, сроки/minimum, stale условия, CSRF, principal isolation, идемпотентность, нормализацию и сохранение адресов. Проверены браузером отрицательный код и полный Packstation→review→TEST order, desktop/mobile. Полный стресс одновременных операций на PostgreSQL не проводился; это не заявление готовности production.
