# Единый вход и MFA — 16.10.2026

## Действующая политика — 22.10.2026

По явному решению владельца MFA добровольна для всех аккаунтов, включая сотрудников и superuser. SHOP_STAFF_MFA_REQUIRED=False в общих settings. Ранее обязательная staff-политика отменена. Уже включённая пользователем MFA продолжает защищать вход штатным allauth challenge; существующие устройства и ключи не удаляются.

## Реализовано локально

Один пользователь Django, пароль и сессия для сайта и рабочего кабинета. `/accounts/login/` использует форму в стиле утверждённой витрины; старые ссылки входа перенаправляются сюда. По умолчанию сотрудник попадает в `/staff/`, покупатель — `/konto/`; безопасный внутренний `next` сохраняется. Права проверяются сервером.

Django/allauth отвечают за пароль, CSRF, подтверждение email, сброс пароля, сессии, ограничения попыток и MFA. Публичная регистрация не выдаёт staff/superuser. Подтверждение email обязательно; восстановление пароля не снимает MFA. Форма работает настоящим POST и исключена из обработчиков demo-прототипа.

Права staff/model permissions и штатная проверка входа защищают `/staff/` и `/admin/`. Отсутствие TOTP не блокирует кабинет и не требует подключения приложения. Настройка MFA доступна по желанию через безопасность аккаунта. Прежний дополнительный staff guard выключен; его opt-in тесты не описывают действующую политику.

Microsoft Authenticator, Google Authenticator и другие стандартные TOTP-приложения подходят без платного SMS-провайдера. После настройки выдаются одноразовые резервные коды; сохранить их сразу в безопасном месте. Любой пользователь, включая сотрудника, может отключить собственный фактор штатной защищённой формой allauth. Право staff не даёт доступ к чужим устройствам. При потере устройства используются резервные коды; восстановление без них остаётся отдельным контролируемым сценарием.

## Настройка разработчика

1. Установить зависимости `uv sync --locked`.
2. Поднять локальные PostgreSQL/Redis по foundation-run.md. Redis используется для общих лимитов и защиты от повторного TOTP, не только для производительности.
3. Добавить в игнорируемый `.env` отдельный `SHOP_MFA_ENCRYPTION_KEYS`. Генерация: `.venv/Scripts/python.exe -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`. Вывод предназначен только владельцу секрета; не сохранять его в Git/логи/скриншоты.
4. Применить `tools/manage_local.py migrate` и запустить сервер как описано в foundation-run.md. Миграции account/mfa уже применены в текущей локальной БД.
5. Создать owner через `createsuperuser`, подтвердить email из локального письма ; TOTP настраивается по желанию через безопасность аккаунта. Отсутствие EmailAddress не считается подтверждением.

Локальный Django использует SMTP существующего Mailpit: 127.0.0.1:1025, интерфейс http://127.0.0.1:8025. Подтверждения регистрации и сброс пароля смотреть там; настоящие письма не отправляются. Контейнер tbmmorpg-mailpit принадлежит другому локальному Compose: его остановка отключит тестовую почту магазина. Старые файлы .local/emails остаются игнорируемыми; новые письма туда не пишутся. Тестовые settings сохраняют locmem backend. Production SMTP, домен отправителя и доставка писем ещё не настроены.

## Секреты и эксплуатация

TOTP-secret и seed резервных кодов шифруются отдельным Fernet-ключом. Нет fallback к plaintext или Django SECRET_KEY. Проверка settings отвергает отсутствие/некорректный ключ. Резервировать ключ отдельно и защищённо вместе с процедурой восстановления БД: потеря ключа лишает возможности расшифровать MFA.

Список ключей через запятую поддерживает чтение старых значений и шифрование новых первым ключом. Простое добавление нового ключа не перешифровывает существующие записи. Старый ключ нельзя удалять до отдельной проверенной миграции шифротекста и восстановления из backup; такой команды пока нет.

Auth-ответы: no-store/private, noindex/nofollow и Referrer-Policy same-origin. Это сохраняет Origin для CSRF при POST и не отправляет адрес с токеном внешним ресурсам. Django dev access log редактирует пути accounts. Это не настройка production proxy/access logs: перед публикацией отдельно настроить их очистку/хранение, HTTPS, cookie flags, trusted proxy/hosts, Redis и email. Текущие внешние шрифты остаются из макета; локальное размещение шрифтов остаётся задачей до production.

Срок сессии и MFA для staff сейчас 8 часов, без запоминания доверенного браузера; изменение срока — явная политика. В БД сохраняются Django user, EmailAddress, Authenticator и сессии; Redis — временные лимиты/replay markers. Пароли, TOTP и recovery-коды не добавляются в бизнес-аудит или аналитику. Retention неактивных аккаунтов, очистка истёкших сессий и production-журналов должны быть настроены до запуска. Новых рекламных событий/согласий эта фича не создаёт.

## Границы и перенос в библиотеку

`web.identity` содержит адаптеры allauth, шифрование, проверку сессии и middleware; allauth владеет моделями MFA. Шаблоны account/mfa принадлежат customer-фиче и используют общую оболочку витрины. Shop role redirects и добровольность MFA для всех ролей остаются политикой магазина.

После обкатки общие механизмы можно вынести в codex-django, сохранив модели allauth, ciphertext, ключи и сессии. На этом этапе библиотека не изменялась. Движок commerce и ARQ не получают auth/Django imports.

Кабинет покупателя восстановлен по согласованному HTML: обзор/профиль/заказы сохраняют reference-композицию; текущие имя/email/год регистрации реальные, безопасность ведёт в allauth. Имя и адресная книга сохраняются в БД; история/показатели/предпочтения пока явно demo. Подробности: customer-account.md. Оплата, eBay и DHL не активировались.
