# Аналитика, согласия и хранение данных

Решение владельца от 15.10.2026: аналитику проектировать вместе с каждой фичей магазина, а не после запуска. Это требования к будущему коду, не реализованная система и не утверждённое юридическое заключение. Цель — полезные и проверяемые данные при минимизации персональных данных; принцип «хранить всё навсегда» не применяется.

## Три потока данных

1. Операционные данные: каталог, SKU, цены, остатки, резервирование, заказ, платёж, отправление, возврат, необходимые сообщения покупателю.
2. Финансовый и служебный audit trail: инициатор/время/основание действия, суммы, изменения состояний, внешние operation/event IDs; отдельные права доступа.
3. Аналитические события: воронка, поиск/фильтры, просмотры, выбор варианта, корзина, привлечение и повторные покупки. У каждого события конкретная цель и классификация; операционное событие не даёт автоматического права передавать его в рекламу.

## Без согласия и с согласием: правила проекта

«Без согласия» означает обработку по другому применимому основанию, а не отсутствие ограничений. Раздельно проверять основание GDPR и доступ/запись на устройстве по § 25 TDDDG. Server-side, first-party и хеширование сами по себе не освобождают от требований; псевдонимизированные данные остаются персональными.

| Данные/цель | Правило допуска | Границы |
|---|---|---|
| Заказ, оплата, доставка, возврат, необходимые письма | В необходимом объёме без отдельного рекламного согласия: исполнение договора/обязательств по применимости | Не добавлять рекламное профилирование и не считать покупку подпиской |
| Финансовые документы и доказательства операций | Законная обязанность/защита требований по применимости | Отдельный график хранения, доступ ограничен; не копировать всё в analytics |
| Необходимые сессии, корзина, CSRF и аутентификация | Без согласия на необязательное отслеживание, только при выполнении критерия необходимости | В cookie/session не прятать рекламный ID |
| Минимальные security/технические журналы | Необходимость и применимое основание, например законный интерес после оценки | Минимизация, короткий срок; не использовать как скрытый clickstream |
| Внутренние отчёты по товарам, остаткам, продажам, комиссиям и возвратам | Неперсональные данные либо документированное основание обработки необходимых бизнес-данных | Повторные покупки по идентифицируемому клиенту требуют отдельной оценки цели/основания; не всё названное аналитикой разрешено автоматически |
| Поведенческий clickstream, межсессионная воронка, необязательные аналитические SDK | По политике проекта — только после отдельного opt-in аналитики, пока иной узкий сценарий не проверен юридически | До согласия не собирать и не буферизовать такие события для последующей отправки |
| Реклама/ремаркетинг, Google Ads теги, рекламные аудитории, передача customer data | Отдельный opt-in рекламы и проверка условий конкретного сервиса/передачи | Никакого автоматического Customer Match из заказов или eBay; серверная пересылка не обходит отказ |
| Email-маркетинг | Отдельный opt-in/DOI и suppression по существующей спецификации | Не объединять с согласием на аналитику; письмо о заказе не зависит от маркетинговой подписки |

Не делаем выводов о сексуальной ориентации, интимной жизни или иных чувствительных характеристиках из покупок белья; не создаём такие профили/рекламные сегменты. Не отправляем третьим сторонам свободный текст поиска, полные URL с PII, адреса, платёжные реквизиты или другие чувствительные поля. Пароли и токены исключены из всех журналов/аналитики.

## Обязательный паспорт данных каждой фичи

При реализации фиксировать в документации фичи:

- бизнес-вопрос и события, кто их создаёт; event name/version, event ID, occurred/received time, источник, operation ID;
- allowlist полей и типов, владельца схемы, минимальный идентификатор; где нужна связь с заказом/клиентом, а где достаточно SKU/агрегата;
- цель, основание GDPR, необходимость согласия и категория, получателей/провайдеров, применимость TDDDG и трансграничных передач;
- срок каждой категории, точку отсчёта, удаление/необратимую анонимизацию, legal hold, поведение backup и сторонних сервисов;
- действия при отказе/отзыве, доступ сотрудников, экспорт/удаление и критерии проверки. Для фичи без аналитических событий явно записать это и причину, не добавлять трекер формально.

Реестр схем версионируется. Устойчивый event ID и дедупликация исключают двойной учёт webhook/retry. Движок производит необходимые доменные факты без импорта Django/ARQ/analytics SDK; адаптеры обеспечивают допустимый сбор/передачу. Необязательная аналитика не блокирует заказ и не подменяет финансовый журнал. Псевдонимные события не связываем с клиентом без документированной цели и основания.

## Сроки хранения и очистка

Предварительные технические значения для обсуждения, не универсальные сроки закона. Перед включением каждой категории утверждаем назначение и срок; если обязательный срок/основание не определены, новый необязательный сбор выключен.

| Категория | Предварительное правило |
|---|---|
| Подробные технические/error логи без лишней PII | 30 дней от события; инциденты — отдельное обоснованное сохранение |
| Сырые необязательные аналитические события | 90 дней от события при действующем основании; отзыв обрабатывается раньше по правилам ниже |
| Персональные/псевдонимные аналитические профили | Не более 12 месяцев от последней разрешённой активности как предварительный предел; более короткий срок по цели, отзыв имеет приоритет |
| Необратимо анонимные агрегаты | Предварительно 24 месяца, затем пересмотр полезности; малые группы и возможность восстановления личности исключаются |
| Заказы, документы, audit и претензии | Раздельные сроки по типам документов и основаниям, утверждённые бухгалтером/юристом; не присваивать всему один срок |
| Доказательство согласия/отзыва, suppression | Минимальные сведения на обоснованный срок для доказательства/предотвращения повторной рекламы; не хранить прежний профиль под этим предлогом |

Периодическая ARQ-задача удаляет/анонимизирует истёкшие данные, формирует безопасный отчёт и сигнализирует о сбоях. Очистка затрагивает выгрузки, кеши и провайдеров по применимости. У backup отдельный ограниченный цикл; восстановление повторно применяет удаления/отзывы до возобновления обработки. Проверять отсутствие PII в анонимных результатах; один хеш не является анонимизацией.

## Согласие и отзыв

- По умолчанию необязательная аналитика и реклама выключены. Независимые категории: analytics, advertising и email marketing. Отказ не мешает покупке; согласия не предустановлены и не объединены с обязательными условиями заказа.
- Сохраняем категорию/цель, версию текста, состояние, время и источник согласия/отзыва с минимальной привязкой. Отзыв доступен не сложнее выдачи согласия; email-отписка доступна без входа по отдельным правилам.
- Контроль на обеих границах: клиент не загружает необязательный SDK/не записывает идентификаторы до согласия; backend проверяет разрешение перед приёмом, сохранением и отправкой соответствующих событий; worker повторно проверяет перед отправкой. При неизвестном/недоступном статусе необязательная обработка запрещена.
- После отзыва прекращаем соответствующий сбор/передачу и отключаем необязательные cookies/идентификаторы в доступной нам области. Несохранённые/очередные события этой цели отменяем; последующая выдача согласия не разрешает задним числом сбор до opt-in. При нескольких устройствах учитываем привязку аккаунта и локальный выбор без навязывания согласия.
- Отзыв не делает прошлую законную обработку незаконной, но не разрешает продолжать её: удаляем/анонимизируем данные, для которых больше нет основания, инициируем обработку у получателей. Не подменяем согласие новым основанием автоматически. Законно необходимые документы заказа и минимальное доказательство выбора сохраняются по своему основанию; рекламный отказ не отключает письма об исполнении заказа.

## Приёмка

До согласия и после отказа: нет необязательных событий, SDK, cookies, пикселей и серверной пересылки. После opt-in включается только выбранная категория. Отзыв во время очереди/ретрая предотвращает отправку; после перезапуска/восстановления запрет сохраняется. Обязательные операции и покупка работают без tracking. Проверяем дедупликацию, сроки удаления, экспорт/доступ и маскирование журналов. В sandbox — только вымышленные данные, без отправки реальных customer lists.

Основания для проектирования: [GDPR, статьи 5–7, 17, 21 и 25](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng/), [§ 25 TDDDG](https://www.gesetze-im-internet.de/ttdsg/__25.html). Финальные цели, основания и сроки согласуются с фактическими сервисами и юридическим пакетом.
