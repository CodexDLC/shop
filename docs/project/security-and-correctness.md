# Код магазина: безопасность и корректность

Технические требования к будущей реализации, 13.10.2026. Это проектирование, не аудит готового приложения и не подтверждение выполненной защиты. Юридические формулировки заказываем отдельно; здесь описан механизм их хранения и использования.

## Деньги

- Денежные значения — Decimal в БД/коде либо целые минимальные единицы валюты на границе API. Float не используется для расчётов.
- Сервер рассчитывает цены, скидки, доставку и итог из доверенных данных. Значения из браузера не являются основанием списания.
- Явные валюта и правила округления; сумма строк, скидок и доставки согласована с суммой платёжного запроса.
- Заказ сохраняет снимок названия/SKU, количества, цены и применённых правил. Позднее изменение каталога не меняет старый заказ.
- Оплата, заказ, отправка и возврат имеют отдельные состояния и разрешённые переходы; одного флага paid недостаточно.

## Платежи

Используем платёжную страницу провайдера. Реквизиты карт и CVV не проходят через наши формы, БД или логи.

- Платёж связывается с конкретным заказом. Проверяем provider account, идентификатор, сумму, валюту и окончательный статус.
- Возврат пользователя на success URL не помечает заказ оплаченным.
- Webhook проверяется по спецификации провайдера: подпись исходного тела, время/защита от повторного воспроизведения, нужный secret. CSRF exemption допустим для этого отдельного endpoint, не для всего API.
- Полученное событие устойчиво сохраняется с уникальным provider/event ID до успешного ответа; обработка идемпотентна. Повторы, иной порядок и задержанные события предусмотрены.
- Создание платежа/возврата имеет устойчивый ключ операции. После timeout сначала выясняем исход операции; новый случайный ключ может привести к повтору.
- Пропущенные события обнаруживаются сверкой с провайдером. Частичные возвраты не могут превысить доступную к возврату сумму; деньги и возврат товара на склад — разные операции.
- Поздняя оплата после истечения резерва обрабатывается явно: повторная проверка остатка, ручное решение/возврат при невозможности исполнения, без скрытого отрицательного остатка.

Источники: [Stripe webhooks](https://docs.stripe.com/webhooks), [идемпотентные запросы](https://docs.stripe.com/api/idempotent_requests). Конкретные правила адаптируем к выбранному провайдеру.

## Заказы и остатки

- Проверка наличия и резервирование выполняются одной транзакцией с блокировкой нужных строк или условным атомарным обновлением. Обычная последовательность «прочитал → уменьшил → сохранил» под конкуренцией недостаточна.
- Ограничения БД защищают уникальные SKU/идентификаторы событий и допустимые количества. Блокировки нескольких SKU берём в стабильном порядке; deadlock обрабатываем ограниченно.
- Резерв имеет срок и явный статус. Освобождение, оплата и отмена не могут дважды вернуть/списать одну единицу.
- Внутри транзакции БД не держим долгие сетевые вызовы. Исходящие задачи сохраняем вместе с изменением состояния в устойчивой очереди/outbox; worker выполняет их после commit.
- Redis не является единственным источником заказов, остатков или финансовых событий. Потеря очереди не должна уничтожать операцию.
- eBay и сайт не разделяют одну транзакцию. Состояние ожидающих обновлений, периодическая сверка, защита от старого снимка и пауза синхронизации обязательны.

Источник: [PostgreSQL row locks](https://www.postgresql.org/docs/current/explicit-locking.html). Проверки конкуренции выполняем на PostgreSQL, не доказываем их SQLite-тестами.

## Аккаунты и права

- Сервер проверяет владельца каждого заказа, адреса, PDF и экспорта данных. Знание UUID/номера заказа не даёт доступ.
- Для гостевого заказа используем ограниченный защищённый механизм доступа, не публичный последовательный ID.
- Отдельные права сотрудников на цены, остатки, возвраты и настройки интеграций. Для сотрудников — MFA; опасные действия журналируются.
- Защита входа и восстановления пароля от перебора; ограниченные по сроку токены. Не раскрываем лишние сведения о существовании аккаунтов.
- Штатные Django auth, password hashing, CSRF и escaping; не пишем собственную криптографию. GET не меняет заказы/остатки.
- HttpOnly/Secure cookies, подходящий SameSite; session rotation при входе. Строгие CORS/allowed hosts, без wildcard по умолчанию.

## Файлы и сторонний HTML

- Фото декодируем и проверяем формат, размеры/число пикселей, общий объём задания. Имя/расширение и Content-Type клиента не являются проверкой содержимого.
- Ограничиваем память/время обработки PNG, размеры загрузок и число файлов; архивы защищаем от path traversal и распаковки чрезмерного объёма.
- Веб-версии фото заново кодируем; исходники не исполняются и не публикуются в каталоге приложения. SVG/HTML не принимаем как обычную фотографию без отдельной обработки.
- Заказы, счета и выгрузки храним приватно; доступ после проверки прав, при необходимости короткоживущие ссылки. Публичные фото отделены от приватных документов.
- Загрузка по URL ограничена разрешёнными источниками; исключаем обращения к внутренней сети/metadata endpoints и проверяем redirects.
- Юридический HTML провайдера проходит контролируемую обработку с разрешёнными тегами/атрибутами. Не используем произвольный mark_safe для любого входящего HTML.

Источники: [Django security](https://docs.djangoproject.com/en/6.0/topics/security/), [deployment checklist](https://docs.djangoproject.com/en/6.0/howto/deployment/checklist/).

## Datenschutzerklärung и другие документы

Планируем отдельный модуль опубликованных юридических текстов: тип документа, язык, версия, источник, дата получения/публикации, checksum, действующее содержимое и история. Конкретный состав и обязательность определяются юридическим пакетом: например Datenschutzerklärung, Impressum, Widerrufsbelehrung/форма, AGB при использовании, сведения об оплате/доставке.

- Документы имеют стабильные URL, доступны без регистрации, ссылки из footer/checkout.
- Обновление API аутентифицировано и атомарно; неполный/ошибочный документ не заменяет действующую версию. Сбой обновления виден сотруднику.
- Версия текста, показанная при оформлении, связывается с заказом там, где это нужно для доказательства условий. Отдельно фиксируются реальные согласия: тип, версия, время, отзыв; не ставим один общий checkbox «согласен на всё».
- Нужные файлы/вложения для письма определяем с юридическим провайдером. Не обещаем автоматически прикладывать весь набор к каждому письму.
- Необязательные scripts/cookies не загружаются до необходимого согласия; отказ и отзыв работают. Установка пакета cookie consent сама это не гарантирует.

Подробности провайдеров: [Datenschutz](../предварительный-стек/datenschutz.md). Тексты должны соответствовать реально подключённым провайдерам и потокам данных.

## Инфраструктура и персональные данные

- HTTPS, корректная доверенная proxy-конфигурация, DEBUG=False, строгие hosts/origins. HSTS включаем после проверки HTTPS. Проверяем Django check --deploy с production settings.
- Секреты раздельны для окружений; ключи имеют минимальные права и план ротации. Postgres/Redis не доступны публично.
- Логи не содержат паролей, OAuth-токенов, карточных данных и полных адресов покупателей. Финансовый audit trail хранит необходимые идентификаторы и изменения, доступ ограничен.
- Сроки хранения задаются по категориям данных. Удаление аккаунта не удаляет безусловно финансовую историю; экспорт и обезличивание учитывают реальные связи моделей.
- Backup включает БД, нужные файлы и конфигурацию восстановления. Проверяем восстановление, а не только наличие копии; реплика/второй сервер не заменяет backup.
- После восстановления до возобновления платежей/продаж сверяем внешние операции: backup может быть старее уже выполненного платежа.
- Мониторим неподтверждённые платежи, зависшие резервы, ошибки eBay, задержку worker и юридических обновлений. Ретраи ограничены; неисправность не скрывается бесконечным повтором.
- Фиксируем зависимости, обновляем security fixes; deploy с миграциями имеет проверенную процедуру восстановления. Production данные не копируем в dev без подходящей обработки.

## Обязательные сценарии приёмки

| Сценарий | Ожидаемый результат |
|---|---|
| Подмена цены/валюты в браузере | Сумма определяется сервером |
| Двойной клик «оплатить», timeout провайдера | Одна логическая платёжная операция |
| Поддельный/повторный/задержанный webhook | Отклонение или безопасная обработка без двойного эффекта |
| Два локальных заказа на последнюю единицу | Только один успешный резерв |
| Оплата после истечения резерва | Явная обработка без отрицательного остатка |
| Запрос чужого заказа/счёта/экспорта | Доступ запрещён |
| Старый снимок eBay после продажи сайта | Ожидающее изменение не потеряно |
| Перезапуск worker после выполнения внешнего вызова | Повтор не создаёт второй платёж/отправление |
| Огромный/повреждённый PNG или опасный архив | Ограниченный отказ без исчерпания сервера |
| Сбой обновления юридических текстов | Последняя версия доступна, ошибка видна |
| Восстановление backup | Сверка внешних операций до продолжения торговли |

Эти проверки добавляются вместе с соответствующими функциями. До закрытия критических сценариев реальные платежи и запись в действующий eBay не включаем.
