# Общий каталог, поиск и фильтры

Задача: [требования, план и независимая приёмка](../../tasks/active/2026-10-20-catalog-database-binding.md). Реализация 20.10.2026; итоговый статус определяется файлом задачи, а не наличием страницы.

## Данные и маршруты

`/katalog/` — основной каталог и поиск. Исторические именованные маршруты `/katalog/suche/`, `/katalog/leer/`, `/katalog/mobil/`, `/katalog/suche/leer/` используют ту же выдачу и согласованную композицию. Пустой результат определяется запросом, не заранее нарисованным сценарием. Отдельный URL мобильного макета не заменяет responsive-проверку основного каталога.

`CatalogPageView` → `ListingRequest` → `ListingContext` → `listing_products/listing_facets` → `product_presentation`. Только активные модели с активным EUR-вариантом. Карточки, цены, цвета, размеры и ссылки PDP берутся из БД; демонстрационные записи seed остаются тестовыми товарами. Фото импортом eBay здесь не пополняются, seed на рабочей базе автоматически не выполняется.

Параметры GET:

| Параметр | Назначение |
|---|---|
| q | Название модели/бренд, активный SKU, slug тега; максимум160 символов |
| brand, category, tag, material, property | Slug справочника; повторные значения — OR внутри поля |
| color, size | Коды/размеры вариантов; повторные значения — OR внутри поля |
| min_price, max_price | Неотрицательный Decimal EUR с точностью до2 знаков |
| in_stock=1 | Ненулевое demo_quantity, ещё не настоящий склад/резерв |
| section | underwear / swimwear / other, классификация Category.section |
| new=1 | Product.new_until не раньше текущей локальной даты, включительно |
| sale=1 | Активный EUR-вариант с is_on_sale=True, совпадающий с остальными variant-фильтрами |
| sort | name, price_asc, price_desc, newest, rating; цена выбранного подходящего варианта |
| page | Страница, по12 карточек |

Разные поля применяются вместе. Цвет, размер, диапазон цены и наличие должны совпасть у одного варианта. Неактивный вариант не может сам обеспечить совпадение. Модель без вариантов не попадает в выдачу. Выбранный начальный SKU и цена сортировки относятся к одному подходящему варианту. Повторные фильтры ограничены20 значениями на поле, фасеты200 значениями на тип; выбранные значения вне списка должны сохраняться при submit и быть явно удаляемыми.

Пагинация, chips удаления и повторная отправка формы сохраняют параметры. Неверные значения показывают локализованную ошибку и безопасно нормализуются; бесконечные/NaN цены и произвольные SQL-поля сортировки не допускаются. QuerySet ограничивается до вычисления карточек. Счётчик реальный, фиксированных24 товаров/трёх страниц нет.

## Компоненты и ограничения

Хедер использует явные Django URL разделов и `/marken/` — отдельный справочник активных брендов с доступными для каталога моделями, по24 бренда на страницу. Он не загружает каталог или справочники на каждой странице. На мобильном используется native details/summary: доступно без JS; JS добавляет Escape с возвратом фокуса, закрытие снаружи и при уходе фокуса. Избранное и корзина работают локально; реальные платежи не подключены.

Метка Neuheiten задаётся в редакторе модели полем new_until, Sale — в матрице вариантов полем is_on_sale; классификация категории доступна через Django admin. Значения по умолчанию null/false не объявляют существующий товар новым или акционным. Sale использует текущую цену и не создаёт зачёркнутую старую цену или процент скидки. Поиск, пагинация и chips сохраняют ограничения раздела. Новая миграция классифицирует только известные seed-категории белья; импортируемые категории требуют явной классификации.

Сохранены reference sidebar, формы, карточки, editorial banner, общий header/footer и существующие токены. На мобильном карточки листаются горизонтально: одна и край следующей. Материалы и свойства — рабочие фильтры структурированных справочников. Newest и рейтинг подключены; популярность остаётся disabled до подтверждённых реальных продаж. Неподтверждённые свойства/состав не выводятся из свободного текста. Новые модальные фильтры не вводятся.

Карточка использует существующий контракт выбора варианта. Цвет определяет набор фото; без отдельных фото цвета используется общая галерея. Нельзя окрашивать фото CSS-фильтром. Изменение размера/цвета проверяется read-only endpoint; отсутствующее сочетание и сетевой сбой не разрешают действие покупки. Кнопка передаёт выбранный SKU в локальную корзину защищённым POST с повторной серверной проверкой. Локальные TEST orders — отдельный реализованный сценарий; реальные оплаты/резервы этим этапом не включаются.

## ORM и проверка

Для непустой серверной выдачи бюджет context —12 SQL: count, страница с FK, варианты/галереи/теги и семь ограниченных запросов фасетов. Полный анонимный HTTP GET дополнительно вычисляет видимость хедера одним запросом. Бюджет сравнивается при1 и12 карточках; это не замер всего HTTP-трафика или PostgreSQL production latency. Первичное отображение read-only карточек не должно повторять variant API-запрос на каждую уже рассчитанную карточку. Последующая проверка выбора пользователя — отдельный запрос и не резервирует товар.

GET не создаёт корзины/заказы/платежи и не вызывает eBay. No tracking SDK, рекламные cookies и аналитические события этим срезом не добавляются. Поисковый запрос участвует в функциональном URL; текущие dev access logs могут его содержать, поэтому нельзя считать отсутствие analytics SDK отсутствием операционного логирования. Политика production-логов остаётся отдельной задачей.

Ручная проверка:

1. Открыть `/katalog/`: реальные карточки и счётчик из текущей базы, без пустых demo-подстановок.
2. Найти модель/бренд/SKU; применить бренд + цвет + размер и диапазон цены; убедиться в выбранном SKU и URL.
3. Открыть неизвестный фильтр/нулевую выдачу, повторить поиск и сортировку — активный фильтр не должен пропадать без явного сброса.
4. Выбрать недоступный размер, поменять цвет; убедиться в сообщении и выключенном действии, затем открыть PDP нужной модели.
5. Проверить телефон390px: нет горизонтального overflow всего документа, карточки прокручиваются внутри ленты, следующий товар виден краем.
6. Пагинацию и неоднозначные сочетания проверить синтетическими данными в тестах; не добавлять и не удалять реальные товары ради демонстрации.

Тесты: `test_catalog_listing.py`, `test_catalog_listing_templates.py`, существующие `test_catalog_queries.py`, `test_catalog_bound_pages.py`, `test_catalog_variant_adapter.py`, `test_storefront_templates.py`. Независимые замечания и их перепроверка — в файле задачи. Автоматические тесты не заменяют browser-приёмку.


### Видимость пунктов хедера (20.10.2026)

Neuheiten, Unterwäsche, Bademode, Marken и Sale скрываются в обоих меню, если нет соответствующих опубликованных моделей с активным EUR-вариантом. Нулевой остаток не скрывает опубликованную модель. Новинки определяются new_until >= localdate; Sale — флагом активного EUR-варианта. Проверка общего хедера выполняет один дополнительный ограниченный SQL с EXISTS, не загружает товары и не использует межзапросный кеш. Она действует также на auth и юридических HTML-страницах; TXT-скачивание без хедера сохраняет SQL0. Feature budget ListingContext SQL10 не меняется. Прямые URL пустых разделов остаются доступными.


## Материалы, свойства, новизна и рейтинг — шаг3, 20.10.2026

Material и ProductProperty: уникальный slug до120 символов, name до160, M2M Product.materials/properties. Редактируются стандартным Django admin; названия — данные справочника, не новые UI-ключи. Назначать только подтверждённые характеристики товара. Текст ProductInformation.composition сам по себе не является нормализованным составом и автоматически не разбирается. Проценты и фильтрация по долям материала этим этапом не введены.

Фильтры material/property работают с поиском, категорией, брендом, тегами и условиями одного подходящего варианта. OR внутри группы, AND между полями. Exists исключает дублирование товара с несколькими связями. Фасеты берутся из активных моделей с активным EUR-вариантом, до200 значений; выбранные неизвестные или вышедшие за cap значения сохраняются в форме и chips (до20 на поле), не пропадают при сортировке/пагинации. На мобильном длинные названия и выбранные значения переносятся без растягивания документа.

`sort=newest` использует nullable Product.published_at: дату первой фактической публикации, заданную по подтверждённым сведениям. Миграция0005 не подставляет дату создания, pk, new_until или время миграции. Неизвестные даты идут последними, равные значения упорядочиваются по имени и pk. Поле не вводит автоматическую публикацию или расписание; будущий workflow первой публикации должен заполнять его осознанно. Метка new_until и сортировка по дате имеют разные назначения.

`sort=rating` использует только approved ProductReview: среднее по всем одобренным оценкам, при равенстве — больше одобренных отзывов, затем имя/pk. Товары без одобренных отзывов идут последними, не получают фиктивный нулевой рейтинг. Агрегаты вычисляются коррелированными SQL subqueries в сортировке, без ORM-запроса на карточку и без повторной загрузки всех отзывов.

Популярность пока выключена: доступная модель оплаты разрешает только demo/sandbox, достоверного источника подтверждённых реальных продаж нет. Тестовые заказы, просмотры и ручные счётчики не заменяют этот источник. `sort=popular` нормализуется к name с понятной ошибкой. Включение требует отдельного решения по источнику продаж, возвратам и периоду расчёта; этого этапа недостаточно.

Новые справочники пусты, published_at старых товаров остаётся NULL, approved reviews отсутствуют на текущей локальной базе. Поэтому текущие материальные/особые фильтры показывают отсутствие значений, а новые сортировки сохраняют стабильный порядок при отсутствии исходных фактов. Sample assignments/дат/оценок в реальный каталог не добавляли. Приёмка положительных совпадений — в изолированной тестовой базе.

Проверки: test_catalog_attributes.py, test_catalog_attribute_templates.py, существующие listing/header sections/template/query tests; browser desktop/390px: newest, rating, selected unknown filters, submit, remove chip, reset и overflow. Контекст12 SQL при1/12 карточках; home5 и PDP9/10 без изменений. Локальный PostgreSQL EXPLAIN newest/rating проверен на четырёх имеющихся товарах, не является нагрузочным benchmark. Новых трекеров/идентификаторов/событий аналитики нет; рейтинг использует уже модерируемый публичный контент без передачи auth данных.
