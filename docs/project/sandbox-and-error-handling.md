# Тестовый стенд и обработка ошибок

Решения владельца от 15.10.2026. Требования к будущей реализации: стенд и перечисленные механизмы пока не собраны.

## Стенд для ручной приёмки

- Работающий Django-магазин, независимый движок и отдельный ARQ worker. Отдельные БД, Redis/очереди, файлы, настройки и ключи; без production-данных. Явная отметка тестового окружения, ограниченный доступ и запрет индексации.
- Оплата через sandbox/test mode выбранного PSP: реальные обращения к тестовому API, тестовая платёжная страница и webhooks, без движения реальных денег. PSP ещё не выбран.
- DHL Shipping, Pickup и Returns — только sandbox endpoints и тестовые реквизиты: этикетки, групповой забор, возвратные PDF и QR. Реального курьера не вызываем. Допустимые данные и ограничения проверяем для каждого API.
- Стенд запрещает live-ключи и production endpoints платёжных/DHL-адаптеров: несовместимая конфигурация блокирует запуск интеграции. Не допускаем переключение в live из клиентского кабинета. Запись в действующий eBay запрещена.
- Письма — в почтовый перехватчик либо выделенные тестовые адреса из разрешённого списка. Данные карт вводятся только в тестовую форму PSP, не в наши формы.
- Физическое движение посылок и недоступные в sandbox события моделируем отдельным тестовым адаптером. В интерфейсе и журнале отличаем симуляцию от ответа sandbox API.
- Ручная приёмка дополняет автотесты: успешная/отклонённая/отменённая оплата; задержанный и повторный webhook; timeout с неизвестным результатом; двойной клик и перезапуск worker; этикетка и групповой забор; возврат товара, проверка сотрудником, полный/частичный refund и его отказ. Письмо об отправке не уходит при создании этикетки.
- Для проверки сохраняем идентификаторы тестовых заказов/операций и ожидаемый/фактический результат, сверяем состояние с кабинетом/API провайдера. Sandbox не доказывает все свойства production; контрольный live-сценарий согласуется отдельно.

## Общий контракт и ошибки фич

- Небольшой общий пакет задаёт базовый тип, формат и общие категории; конкретные ошибки принадлежат фичам. Один класс — один файл. Не создаём единый файл со всеми ошибками и бизнес-правилами.
- Движок не зависит от Django, HTTP, ARQ и языка интерфейса. Ожидаемые отказы — явные доменные ошибки/результаты со стабильным `code`, безопасными параметрами и допустимым действием. Конкретную форму выбираем при реализации и применяем последовательно.
- Django-адаптер переводит доменные причины, ошибки forms/auth/permissions и известных внешних адаптеров в корректный HTTP-статус, код и локализованный текст. Штатные механизмы Django сохраняем; не заменяем все стандартные исключения. Тексты и переводы — ответственность web-слоя; немецкий основной.
- Общий реестр отображений код → ключ перевода/допустимые действия расширяется из фич. Frontend реагирует на код, не разбирает текст сообщения.
- Ответ API содержит `code`, безопасный `message`, `request_id`, при необходимости `field_errors`, `operation_id`, `action`. HTML/HTMX показывает ту же причину у поля, в форме или блоке состояния, сохраняет безопасные введённые данные. Никаких traceback, SQL, ключей и необработанных ответов провайдера пользователю.
- Примеры: `catalog.variant_unavailable` → выбрать другой вариант; `orders.invalid_address` → исправить конкретные поля; `payments.refund_exceeds_remaining` → показать сотруднику доступную сумму; `payments.outcome_unknown` → «Проверяем результат операции», без предложения повторной выплаты; `shipping.temporarily_unavailable` → сохранить состояние и показать дальнейшее действие.
- Сохраняем смысл HTTP-кодов: валидация не превращается в 404, внутренний сбой — в успешный 200. Настоящие 403/404/500 имеют понятные страницы; ответы о чужих ресурсах не раскрывают их существование.
- Неожиданный сбой перехватывается на границе web-приложения/задачи и журналируется; пользователю — безопасный текст с номером обращения. Не подавляем исключение и не маскируем отказ успехом.

## Журнал, реакции и защита от дублей

- Журнал: окружение, фича, код ошибки, request/correlation ID, operation ID, ID запроса провайдера, время, попытка и результат. Финансовый audit trail отдельно хранит инициатора, сумму, валюту, основания и изменения состояния. Доступ и сроки хранения ограничены. Не пишем пароли, токены, данные карт и полные адреса; PII маскируем.
- Состояния операций различают ожидание, выполнение, успех, окончательный отказ и неизвестный исход. Timeout после отправки запроса не доказывает отказ: сначала сверяем результат, не создаём новую выплату/заявку.
- Устойчивые ключи логических операций, уникальные ограничения и транзакции защищают от параллельных запросов, двойного клика, повторных webhook и перезапуска worker. Блокировка кнопки — только UX. Внешнюю идемпотентность проверяем для конкретного API: локальная дедупликация не гарантирует отсутствие дубля у провайдера.
- Повторы — только для классифицированных временных сбоев и безопасных операций, с лимитом попыток, backoff и учётом квот. Ошибки данных/прав/бизнес-правил не повторяем вслепую. После лимита — видимое состояние и действие сотрудника.
- Refund запускает сотрудник с подтверждением суммы, не событие DHL. Обязательные сроки возмещения проверяются отдельно.
- При реализации каждой фичи проверяем код, текст, HTTP-статус, доступ к данным, восстановление и отсутствие повторного эффекта. Для финансовых операций обязательны конкурентные запросы и неизвестный исход.
