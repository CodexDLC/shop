# eBay: уведомления об удалении аккаунта

Статус: обработчик тестового стенда, 16.10.2026. Не выполняет запись, удаление,
изменение остатков или объявлений на eBay. Не является готовым процессом удаления
импортированных персональных данных.

## Подключение

- Django app: `web.ebay_notifications` в `INSTALLED_APPS`.
- URL вне `i18n_patterns`: `path("integrations/ebay/", include("web.ebay_notifications.urls"))`.
- Применить миграцию `ebay_notifications.0001_initial` на отдельной БД магазина.
- `EBAY_NOTIFICATION_ENDPOINT=https://shop.pinlite.dev/integrations/ebay/account-deletion/`.
- `EBAY_NOTIFICATION_VERIFICATION_TOKEN`: случайный секрет длиной 32–80 символов,
  только латинские буквы, цифры, `_` и `-`. Сохранять в закрытом серверном env.
- `EBAY_APP_ID` и `EBAY_CERT_ID`: Production Client ID / Client Secret. `DEV_ID`
  этому обработчику не требуется. Значения не публиковать в документации и логах.
- Redis — общий cache backend всех процессов Django для ключей и application token.
- Обработчик должен быть доступен без HTTP Basic Auth; остальные страницы стенда
  могут быть закрыты паролем. HTTPS обязателен. Нужен доступ сервера к `api.ebay.com:443`.

В портале eBay в Marketplace Account Deletion указать alert email, точный endpoint
и verification token. При сохранении eBay выполнит GET challenge. Проверка GET
не требует application token: это позволяет активировать отключённый keyset.
После активации вызвать **Send Test Notification** и убедиться, что появилась
подписанная запись в Django admin. Локальные автоматические тесты сетевых вызовов
не делают, ключи и реальные аккаунты не используют.

## Верификация и ограничения

GET возвращает SHA-256 от `challenge_code + verification_token + exact_endpoint`.
Host входящего запроса не участвует в вычислении. Пустой, повторный или слишком
длинный challenge отвергается. Конфигурация с неверным секретом даёт 503.

POST принимает только JSON до 64 KiB. CSRF отключён только на этом endpoint,
вместо сессии обязательна подпись `X-EBAY-SIGNATURE`: Base64 JSON с полями
`kid`, `signature`, `alg`, `digest`. `kid` ограничен безопасным набором символов;
произвольные URL из запроса не используются.

**Не путать алгоритмы:** официальный Node SDK eBay использует `ssl3-sha1` для
подписи уведомления, а SHA-256 — для challenge. Здесь разрешены ECDSA / SHA1
и DER-подпись, проверяемая `cryptography` над исходными байтами body. Другие
алгоритмы отвергаются, автоматического fallback нет. Это протокол провайдера,
а не выбор SHA1 для новых механизмов магазина. Реальная тестовая доставка eBay
остаётся обязательной внешней приёмкой: стенд не должен скрывать несовместимость
формата или алгоритма успешным ответом.

Для получения публичного ключа используются только фиксированные адреса eBay:

- POST `/identity/v1/oauth2/token` — техническая аутентификация приложения;
- GET `/commerce/notification/v1/public_key/{kid}` — чтение ключа.

Они не изменяют товары/заказы. Редиректы не выполняются, TLS проверяется,
таймаут соединения/чтения 5 секунд, ответ ограничен 32 KiB. Публичный ключ
кэшируется на час; application token — не дольше часа и меньше его срока действия.
Отсутствие ключей, недоступность eBay/cache/БД дают 503, неверная подпись — 412.
Неподдерживаемый topic/schema — 400. Без подписи положительного ACK нет.

## Долговременная квитанция и ручной процесс

200 означает только: подпись проверена, receipt успешно сохранён в PostgreSQL.
Статус записи — `review_required`, а не «данные удалены». В admin квитанции
доступны только для чтения, без массовых действий. Защита staff/MFA общая.

Сохраняются notification ID, topic/schema, дата события/приёма, fingerprint
стабильного события, HMAC userId и статус. Сырые body, username, eiasToken и
userId не сохраняются и не журналируются. Fingerprint не включает изменяемые
поля доставки `publishDate` / `publishAttemptCount`: повторы одного события
допустимы; изменение данных под прежним ID даёт 409. Уникальное ограничение
notification ID и транзакция защищают от одновременного повторного приёма.

HMAC использует Django SECRET_KEY с отдельным salt. Это псевдонимизация, не
анонимизация. Для сопоставления будущий импорт должен применять тот же контракт
идентификатора и обеспечивать сохранение/контролируемую ротацию ключа. Сейчас
сырых идентификаторов в receipt нет, поэтому восстановить пользователя по нему
невозможно. Уведомления нельзя считать разрешёнными только из-за успешного ACK.

До импорта eBay-данных необходимо реализовать и проверить сопоставление записей,
удаление/обезличивание, документирование законных исключений и работу с backup.
Сейчас оператор проверяет квитанцию и отсутствие затронутых данных вручную;
это ограничение тестового стенда. Не включать импорт персональных данных, пока
нет полного процесса. Объявления eBay этим процессом не удаляются.

Основание хранения receipt — соблюдение требований интеграции/обработка запросов
удаления, согласие на маркетинг не используется. На тестовом стенде хранить
квитанции до завершения проверки интеграции и ручного разбора, затем удалить
тестовые записи по согласованной операции. Production retention и периодические
очистки ещё не утверждены; бессрочное накопление не разрешено. Связанный экспорт,
логи прокси и резервные копии входят в будущий паспорт хранения данных.

Ни один тест не обращается к внешним API. Интеграционная приёмка после деплоя:
challenge через портал, подписанное test notification, проверка receipt/admin,
проверка отказа unsigned POST и отсутствия PII/секретов в журналах.
