# Редактор товара в существующем кабинете

Контракт22.10.2026; реализация и результаты проверки — в [задаче](../../tasks/active/2026-10-22-staff-product-editor.md). Это K1 из [очереди кабинета](staff-cabinet-roadmap.md). Остальные K2–K8 не реализуются автоматически.

## Работа сотрудника

Вход через прежнюю форму сайта, MFA по желанию; кабинет `/staff/catalog/`, существующая оболочка codex-django и её тема. У товара вкладки: основные данные, варианты, тексты/характеристики, фотографии, проверка/публикация и закрытый предпросмотр.

1. Создать черновик: бренд, категория, название, артикул, slug, теги, материалы/свойства. Сохранение не включает is_active; существующий description_key оставлен только для чтения как legacy.
2. Создать варианты с SKU/цветом/размером и условными ценами/количествами. Существующие SKU неизменяемы. Технические ключи названий цветов прежней матрицы сохраняются; удобные справочники и импорт — следующие K2/K3, не новый механизм перевода в этом шаге.
3. Внести обычным текстом немецкое описание, состав, уход, посадку, происхождение и подтверждённые сертификаты. Неизвестные сведения оставлять пустыми. Размерные таблицы остаются общими для бренда/категории; вкладка показывает существующие таблицы, не создаёт копию на каждую модель.
4. Загрузить фото и выбрать галерею цвета либо общий fallback. Разные размеры используют галерею одного цвета. Настроить порядок и alt-текст.
5. Посмотреть закрытый предпросмотр в композиции реального PDP. Покупка/избранное в нём выключены; публичный PDP черновика возвращает404. Preview защищён staff/model permission, no-store/private и noindex.
6. Проверить текущие данные: обязательны базовые поля, описание (включая действующий legacy fallback), хотя бы один активный SKU, конечная положительная цена EUR для каждого активного варианта и подходящие фото каждого активного цвета (или общий fallback). Остаток не обязан быть положительным: это не реальное подтверждение склада.
7. С отдельным правом публикации включить видимость в локальной витрине. Последующая правка требует явного снятия в черновик, о чём интерфейс предупреждает. При снятии товар исчезает из каталога/PDP; после правок нужна новая проверка.

Первая версия не поддерживает параллельную живую и новую черновую редакции. Проверка готовности — проверка структуры и полноты, не подтверждение правдивости введённых сотрудником сведений. Это не публикация на eBay и не открытие индексации стенда.

## Права и непротиворечивость

Проверка не равна публикации. Последняя требует `catalog.publish_product` вместе с правами просмотра/изменения товара. Права модели отдельно управляют текстами, вариантами и photo create/update/delete. Новое разрешение автоматически существующим сотрудникам не назначается. Владельцу-суперпользователю оно доступно штатным способом Django.

Product, ProductVariant, ProductInformation и ProductImage в стандартном Django admin становятся только для просмотра: это исключает обход рабочего процесса через второй интерфейс. Справочники, размерные таблицы и модерация отзывов сохраняют прежний admin; K2 даст им удобные рабочие экраны.

Каждая mutation — POST+CSRF с parent Product select_for_update внутри atomic. Подписанный снимок защищает от перезаписи устаревших форм; fingerprint проверки учитывает данные товара, справочники/M2M, информацию, варианты и фото. Изменение отменяет готовность; повторное/устаревшее подтверждение не считается новой успешной публикацией. Audit сохраняет actor/action/object/time, не payload форм или изображения.

`editorial_state/review_fingerprint` дополняют прежнее is_active; действующая видимость сохраняется. Миграции0006/0007 не заполняют опубликованным товарам неизвестный published_at текущей датой. Дата первой новой публикации создаётся только после явного действия сотрудника. SEO-флаги и demo markers этим не снимаются.

## Фотографии и storage

JPEG/PNG/WebP проверяются по фактическим байтам Pillow: до8МБ входа/выхода,16МП,8000px по стороне, без анимации. После EXIF orientation изображение сохраняется без метаданных в новый JPEG либо PNG с UUID-именем; исходный файл на компьютере не перезаписывается. SVG/HTML/невалидные и слишком большие изображения отвергаются сервером.

На модель не более100 изображений; позиции0–99. Перестановка и смена цвета проходят транзакционно без временного нарушения уникальности. Цвет берётся из вариантов; изображения общего fallback не требуют отдельной копии по размеру. Список фото не делает запрос на каждую карточку для повторного чтения цветов.

`ProductImage.file/alt_text/public_url` дополняют старые image_url/alt_key. URL-фотографии сохраняются, внешний URL не скачивается новым редактором. Витрина/вариантный API/корзина используют public_url; новый alt имеет приоритет перед старым ключом. В локальном DEBUG media обслуживается по `/media/`; в staging/production нужен отдельно настроенный media delivery, этот шаг его не разворачивает.

При откате новой загрузки созданный файл очищается. Замена/удаление связи намеренно не удаляет прежние физические объекты: они могут быть нужны для отката/backup. Последующая безопасная очистка потребует сверки ссылок и политики хранения, а не удаления всего каталога. Сохранение оригинала загрузки отдельно от нормализованной копии/производных и S3 — следующие возможности.

## Данные и границы

Товарные тексты/изображения и функциональные editorial state не являются маркетинговой аналитикой. Новых cookies/tracking/SMTP/API нет; audit имеет собственное служебное назначение, production retention остаётся эксплуатационной задачей. Локальные тестовые цены/остатки не превращаются в реальные offers/выручку. Файлы персональных документов сюда не попадают.

Полный PostgreSQL concurrency stress не заменяется SQLite-тестом. Реальная отправка на eBay, оплаты/DHL/S3, deploy и git-публикация в K1 не входят.
