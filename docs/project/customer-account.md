# Кабинет покупателя

Кабинет восстановлен из согласованных HTML-референсов, а не из упрощённой страницы авторизации. Основные страницы — `/konto/` (обзор) и `/konto/profil/` (личные данные, безопасность, адреса и предпочтения). Сохраняются композиция, боковая навигация, карточки показателей, заказы и остальные блоки исходного макета. Общие header/footer и токены остаются в существующей системе сайта.

## Реальные возможности

- Доступ требует входа через общую форму `/accounts/login/`; используется текущая Django-сессия.
- Имя берётся из `user.get_full_name()`, при его отсутствии показывается username. Email и год регистрации принадлежат текущему пользователю, а не персонажу из макета. Вывод экранируется Django Templates.
- В обзор и профиль добавлен блок безопасности аккаунта: настоящие переходы на управление email, смену пароля, MFA и выход через allauth. Выход завершается штатным защищённым POST, а не ссылкой, удаляющей сессию через GET.
- Сотрудник использует ту же учётную запись; доступ к рабочему кабинету определяется серверными правами и политикой обязательного MFA. Клиентская страница не выдаёт права сотрудника.

## Что остаётся демонстрацией

Показатели покупок, примерочные сценарии, история и состав заказов, персонализация, клубные преимущества, синхронизация счетов и рекламные предпочтения остаются демонстрационными, пока их backend не реализован. Они сохраняют места и оформление из референса и явно помечаются как preview/demo. Демонстрационные цифры не являются реальными данными пользователя или обещанием условий магазина.

Демонстрационные формы не должны заявлять об успешном сохранении данных, смене пароля или принятии рекламного согласия. Формы имени и адресов теперь реальные, имеют data-real-auth и не перехватываются demo-обработчиками. POST на страницу профиля не поддерживается (405); реальные операции безопасности доступны через allauth. Пароль нельзя вводить в демонстрационную форму: её поля отключены, рядом есть настоящий переход смены пароля.

`customer-account.js` перехватывает отправку демонстрационных форм до исходных inline-обработчиков и показывает сообщение о демонстрации вместо сохранения. На странице профиля он также заменяет `window.showToast`: исходные интеракции макета остаются, но сообщения не утверждают, что адрес или предпочтения записаны на сервер. Демонстрационные контактные действия с `data-customer-demo-action` не открывают выдуманные телефонные номера или WhatsApp. Настоящие ссылки безопасности не должны попадать под этот перехват.

## Разделы и дальнейшее расширение

«Личные данные и безопасность» — настройки личности, email, пароля и MFA. «Адреса» — реальные сохранённые адреса доставки; синхронизация адреса счёта остаётся будущей функцией. «Предпочтения» — персонализация и коммуникации; будущие рекламные согласия требуют отдельной реализации хранения, подтверждения и отзыва. Эти группы уже представлены в референсе: расширяем их внутри существующей структуры, не заменяя кабинет техническим списком ссылок.

Не включать эти функции визуальным toast-сообщением: сначала необходимы модель, права текущего владельца, серверная валидация, CSRF, обработка ошибок и проверка результата. Чужие заказы и адреса никогда не доступны по одному лишь переданному ID.

## Проверка

`tests/web/test_customer_account.py` проверяет общую точку входа, текущую и экранированную личность, fallback имени, сохранение ключевых элементов референса, настоящие ссылки безопасности и невозможность изменить пользователя демонстрационным POST. Тесты используют временную SQLite-базу и не создают пользователей или письма в рабочей локальной базе. Визуальная приёмка desktop/mobile проверяется отдельно в браузере.

## Сохранение имени и адресов — 16.10.2026

Локальная миграция customer.0001_initial применена. Можно вручную проверить: войти → /konto/profil/ → изменить имя → сохранить и обновить страницу; открыть вкладку адресов → создать, отредактировать, сделать основным или удалить адрес. Основной адрес показывается также в обзоре /konto/. У новой учётной записи пустой список, вымышленные адреса референса больше не выдаются за данные пользователя.

Одно поле полного имени сохраняется в User.first_name (до 150 символов), last_name очищается: мы не угадываем разделение составных имён/фамилий. Email и права этой формой не меняются. Изменение имени не переписывает имя получателя уже сохранённого адреса. Обращение и телефон остаются отключёнными полями референса, их хранение не реализовано.

CustomerAddress: владелец, тип standard/packstation, получатель, улица с номером дома либо Postnummer+Packstation, PLZ, город, DE, is_default и времена создания/обновления. Поддержана только Германия; PLZ — пять ASCII-цифр. Packstation-поля проходят локальную проверку формата (Postnummer 6–10 цифр, станция 1–5); это не подтверждение адреса или принадлежности Postnummer со стороны DHL. Внешний DHL API не вызывается. Адрес счёта/checkout/order snapshots этим изменением не реализованы.

Первый адрес становится основным. Владелец может сменить основной; после удаления основного выбирается первый оставшийся, после удаления последнего список пуст. Ограничение БД допускает не более одного основного адреса пользователя. Все изменения адресов идут в atomic transaction с блокировкой User через select_for_update; разные пользователи не блокируют адресные книги друг друга. Контроль гонок SQL структурно предусмотрен, отдельный параллельный PostgreSQL stress-test не проводился.

Все mutation endpoints требуют входа, POST и CSRF. Владелец определяется сессией, user из POST не принимается; чужой адрес даёт 404, даже если текущий пользователь staff. Неверная форма возвращает 400 в том же дизайне с исходными значениями/ошибками и открытым модальным окном. Изменения персональных данных используют PRG redirect+сообщение. Customer ответы private/no-store/noindex; данные адресов для редактирования передаются только владельцу через безопасный json_script. Адресный queryset вычисляется один раз для карточек/JSON/default, без запроса на каждую карточку.

## Паспорт данных этой фичи

- Цель: запрошенное пользователем хранение имени и адресной книги для аккаунта и будущего оформления; операционные данные, без новых аналитических/рекламных событий. Новых cookies/SDK/согласий не добавлено.
- Allowlist: поля модели выше и first_name/last_name. Не хранить POST-дампы, историю старых адресов, устройство, геолокацию или маркетинговый профиль в рамках этих сохранений. Postnummer не логировать. Текущее событие не отправляется ARQ/DHL/eBay/платёжному провайдеру.
- Доступ: собственный аккаунт; страницы и mutations проверяют владельца. Штатный model FK CASCADE удаляет адреса при удалении User, но публичный сценарий удаления аккаунта ещё не реализован.
- Хранение: текущая запись до изменения/удаления пользователем либо удаления аккаунта; удаление адреса сразу убирает строку из активной БД. Исторические order snapshots не созданы этим этапом и впоследствии будут отдельной категорией с собственным сроком. Финансовые сроки не применяются автоматически к адресной книге.
- Для production: подтвердить основание обработки при утверждении Datenschutzerklärung, цикл неактивных аккаунтов и backup retention/replay удалений. До этого не добавлять необязательную аналитику. В локальных проверках используются вымышленные данные.

Проверки backend: tests/web/test_customer_persistence.py — валидация, owner isolation, CSRF, запрет GET mutation, игнорирование email/прав, default rules и ограничение БД. Ручной browser flow работает на локальном PostgreSQL; evidence visuals/customer-persistence. После проверки временные аккаунты/адреса удаляются; реальные пользовательские записи не изменяются.

Итог сохранения: 230 pytest passed, Ruff clean, Django check и makemigrations --check без ошибок. Chromium на локальном PostgreSQL подтвердил имя после reload, создание/изменение обычного адреса, Packstation, смену основного, отображение в обзоре, удаление/default fallback и сохранение невалидной формы с ошибкой. На mobile document overflow отсутствует, JS errors нет. Временные аккаунты/сессии/адреса удалены, пользовательские данные не изменялись. Коммит/push этого этапа не выполнялись.
